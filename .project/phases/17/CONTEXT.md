# Phase 17 context

Confirmed assumptions and answers from the phase start (2026-11-22).

- The MCP server lives in `internal/cli/mcp.go`; `cli.Run` serves it over `mcp.IOTransport` on `IO.Stdin`/`IO.Stdout`; `cmd/hlab/main.go` stays unchanged.
- `mcp` is in the commands table without `--output`; `cli.Commands()` lists it without `--output`; `hlab mcp --output json` is a usage error.
- Each tool reuses its command function with JSON output and returns its own `*mcp.CallToolResult` with text content only (no structured content, no output schema); the text is what `--output json` gives.
- A command error is an MCP tool error (`isError`) with the message `hlab` prints; with the cloud stopped it says "the cloud is not running"; the server keeps serving until stdin closes or ctx ends.
- `cli.NewMCPServer(sys IO, opts MCPOptions) *mcp.Server` and `cli.MCPTools() []string` are exported; `MCPOptions` holds the cloud wait limit (default 5 min), the poll interval (about 1 s) and the progress interval (about 10 s).
- Tool arguments in snake_case: `project_create {display_name}`, `project_delete {name}`, `token_create {project, name, read_only?}`, `token_list {project}`, `token_revoke {project, name}`, `logs {lines?}`, `ca_trust {on}`; `cloud_status`, `cloud_start`, `cloud_stop`, `project_list`, `ca_export`, `version` take none.
- `cloud_start`/`cloud_stop` never pass `discard-state`; they read `Service.State` first: already in the target state returns the status at once without error (like `hlab cloud start`/`stop`); a running transition is waited for (`starting` -> `running`, `stopping` -> `stopped`, the opposite transition first waited out, then acted on), all within the one 5-minute limit.
- After its own start, `stopped` counts as final only if the service was seen not stopped or `status.json` is newer than the request; `stopped` with `refused` or `error` is a tool error; the time limit gives "still not running after 5m0s".
- `project_delete` waits with the existing 30-minute `projectDeleteTimeout`; on `409` it waits for the `action_id` in the conflict answer (Q20).
- Q1 answer: the `409 conflict` of `DELETE /projects/{name}` carries `action_id` of the running deletion (additive, ARCHITECTURE.md updated); a unit test in `internal/mgmt` checks the 409 answer contains that action ID; `hlab project delete` keeps printing the conflict message.
- Progress: with a `progressToken` from the client, `cloud_start`, `cloud_stop` and `project_delete` send a progress notification about every 10 s with the current state (`project_delete` with the action's progress); without a token none.
- Client cancel (request ctx ended) ends only the wait; start, stop or deletion continues in hlabd; a repeated call waits for the running operation instead of failing.
- `logs`: explicit input schema, `lines` minimum 1, maximum 1000, default 200; a value outside is a tool error; while running it reads the fixed 1000 lines of `GET /logs` (`mgmt.LogLines`) and keeps the last N, while stopped `logfile.Tail(dir, "hlabd.log", N, false, ...)`; result is raw JSON lines; the management API is otherwise unchanged.
- `ca_export` returns the PEM as text and writes no file; `project_list` returns the unchanged `GET /projects` JSON; `token_create` returns the token JSON plus a text item that the value cannot be retrieved again; `token_list` has no values.
- No tool for `catalog update` or `--discard-state`.
- Server implementation name `hlab`, version `version.Version`; diagnostics only on stderr, stdout carries protocol messages only.
- Unit tests (`internal/cli/mcp_test.go`, group `TestMCP`): in-memory go-sdk client against a fake management API and fake service, never the real service; one case per tool, one for the stopped cloud (MCP-02); further cases only for MCP-03/04 promises (wait time limit, start refused, stale `status.json`, `token_list` without values), one for progress notifications, one for a cancel after which the operation continues, one for the 409 wait; no test checks schema or registration of single tools.
- MCP-05 e2e: starts the `bin/hlab.exe` built in this run with `mcp` over the go-sdk `CommandTransport`; runs `project_create`, `token_create`, `project_delete` against the dev service with a deadline per call; the display name begins with the runID so `leftoverProject` finds it; `project_delete` is also in `t.Cleanup`.
- Docs: section `hlab mcp` in `docs/commands.md` with every tool, arguments, results, stopped-cloud behaviour, examples for Claude Code (`claude mcp add --transport stdio --scope user hlab -- <path>\hlab.exe mcp`) and Claude Desktop (`%APPDATA%\Claude\claude_desktop_config.json`); one sentence that a client with a short per-call limit (Claude Desktop probably about 60 s) may cancel the wait while the operation continues and `cloud_status`/`project_list` show its state; a short note in `README.md`; no checked-in `.mcp.json`; the DOC-01 test covers the tools.
