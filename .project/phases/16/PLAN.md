## Findings from manual testing

- bug (2026-11-25, /wcc:report): DOC-08. The "Create the VM" block of `docs/development/release-checks.md` fails on a Windows host in another language. The user pasted it on a German Windows 11 in an elevated PowerShell; `Enable-VMIntegrationService -VMName $Name -Name 'Guest Service Interface'` stopped with "Es wurde keine Integrationskomponente mit dem angegebenen Namen gefunden." (InvalidParameter, VirtualizationException), because the integration service's display name is translated. DOC-08 expects every command of the guide to run as written. Fix: select the service by its fixed ID instead of its name, as `internal/platform/hyperv/hyperv.go` already does for the Shutdown service, e.g. `Get-VMIntegrationService -VMName $Name | Where-Object { $_.Id -like '*6C09BB55-D683-4DA0-8931-C9BF705F6480' } | Enable-VMIntegrationService` (confirm the ID of "Guest Service Interface" against Microsoft's documentation or a host). Replace the note about translated names under "What the block sets and why" accordingly. In the same pass, check the guide for other language-dependent names: the `autounattend.xml` creates the local account in `<Group>Administrators</Group>`, which on a German Windows ISO is "Administratoren"; make it work for any ISO language (or tell the reader plainly which name to use), and check any later command that names a service, group or component by display name (Copy-VMFile steps, checkpoint names are fine). `TestDocs` must stay green.
- minor (2026-11-25, /wcc:report): DOC-08. In `docs/development/release-checks.md`, "Install Windows", the three ways to a local account ("Answer file (first choice)", "Domain join instead", "Setup without network") are only bold paragraphs in a row. The user reading the guide could not tell that exactly one of them is chosen, nor where one way ends and the shared steps ("Then start the VM and open its console", the setup steps, removing the ISOs) begin. Fix: open the section with one sentence saying to pick one of three ways, in the order to try them, as a short list that says when each acts (answer file: before the first start; setup without network: disconnect before the start, reconnect after the first sign-in; domain join: during setup on the account screen). Give each way a subheading of its own, and the shared part a heading of its own (e.g. "Start the VM and run setup") that refers back to the step of the chosen way where it applies (reconnecting the network after sign-in). Keep the section anchors that CHECKS.md and other guides link to, or update the links; `TestDocs` must stay green.
- change (2026-11-25, /wcc:report): DOC-08. The user asked why the answer file does not run the whole installation; one way is easier to follow and to repeat. Changed: DECISIONS.md "2026-11-25 Windows in the test VMs installed fully by the answer file" (replaces "Answer-file ISO built with IMAPI2" and "Local account at Windows setup left to the guide"), CHECKS.md DOC-08 steps 2 and 3. Build in `docs/development/release-checks.md`, "Install Windows" and "Enable Hyper-V in the VM": the answer file gets a windowsPE pass (setup and input language from a variable at the top of the block, e.g. `$Lang = 'de-DE'`, which must match the ISO's language; disk 0 wiped and partitioned for UEFI/Generation 2: EFI, MSR, Windows; Windows 11 Pro chosen without activation, e.g. with Microsoft's generic Pro installation key, to be confirmed against Microsoft's documentation; licence terms accepted) and a fuller oobeSystem pass (local account as now, online account and privacy screens hidden, one automatic sign-in with `LogonCount` 1, first-logon commands that enable `Microsoft-Hyper-V` with all sub-features and restart the VM). The user only starts the VM, presses a key for "boot from CD or DVD", and waits; the guide says how to see that it is done (after the restart, sign in; `Get-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V` shows Enabled). "Domain join instead" and "Setup without network" are removed, and the manual setup steps (product key, edition, disk) go with them; "Enable Hyper-V in the VM" shrinks to the check and the existing note on nested virtualization. The answer file must stay language-independent apart from `$Lang` (see the bug above on `Administrators`). The password stays asked with `Read-Host`, and the answer file folder and ISO are still deleted after setup. This change supersedes the minor finding above on the three ways in "Install Windows": with one way, that structure problem is gone; keep a clear heading for the shared part (start the VM, remove the ISOs afterwards). `TestDocs` must stay green.
