## 2. Hetzner Storage Box SSH side

Primary sources: docs.hetzner.com/storage/storage-box/access/access-ssh-rsync-borg/, .../access/access-sftp-scp/, .../ssh-keys/add-ssh-keys/ (also at .../backup-space-ssh-keys/), .../general, .../access/access-overview/, docs.hetzner.com/robot/storage-box/available-disk-space.

- Ports (CONFIRMED): 22 = SFTP/SCP, always on, no interactive access; 23 = SFTP/SCP, rsync, BorgBackup and a restricted command set, only when SSH support is enabled. External access needs "External Reachability". Subaccounts connect to `uXXXXX-subX.your-storagebox.de` with the subaccount's own user name on the same ports.
- Port 23 commands (CONFIRMED): cd, ls, stat, pwd, tree, du, df, dd, chmod, mkdir, rmdir, touch, cat, cp, mv, rm, unlink, head, tail, md5/sha1/sha256/sha512 (and `*sum`), grep, version, help. No full shell, no pipes or redirects, uploaded scripts cannot run. Borg: `--remote-path=borg-1.1|borg-1.2|borg-1.4` (default 1.2). `install-ssh-key` is a command on port 23 that reads a public key on stdin.
- Login directory and path seen: the docs say "Only the directory `/home/` is writable" and recommend relative paths (`server1/x` equals `./server1/x`); they do not state the landing directory. A search summary says a session starts in the home directory and an upload shows as `/home/<file>` (secondary, INFERRED). So: the login lands in the box's home, shown as `/home` (UNCONFIRMED whether `pwd` prints `/home`; E17's design uses `internal-sftp -d /home`, which matches). Creating `/etc` and `/lib` is not possible. Do not remove the execute bit of the home directory (login then fails).
- Keys: docs (SSH section) say port 23 needs normal OpenSSH one-line format and not RFC4716. The key guide says: Option 1 `install-ssh-key` over port 23 installs the key in both RFC4716 (port 22) and OpenSSH format (port 23), keeping existing keys; Option 2 (`ssh-copy-id -p 23 -s`, or scp) writes OpenSSH format to `.ssh/authorized_keys` and only works for port 23; Option 3 writes RFC4716 for port 22 only. Options 2 and 3 overwrite the whole file, including "a key added when the Storage Box was created". The general page: both formats go in the same `.ssh/authorized_keys`, file must end in a newline. CONFIRMED: file is `.ssh/authorized_keys` in the box's home; port 22 needs RFC4716 blocks (`---- BEGIN SSH2 PUBLIC KEY ----`), port 23 needs OpenSSH lines.
- `ssh_keys` at creation: the OpenAPI spec says "SSH public keys in OpenSSH format to inject into the Storage Box" (docs.hetzner.cloud/hetzner.spec.json, create_storage_box). The key guide implies they end up in `.ssh/authorized_keys`. UNCONFIRMED: whether Hetzner also writes the RFC4716 form so that port 22 accepts them at once; the guide ("each option configures only one port") suggests creation-time keys serve port 23 only. Safest for hlab: write both formats into `.ssh/authorized_keys` for each key and have `install-ssh-key` do the same.
- Subaccounts (CONFIRMED): "Each sub-account requires its own `authorized_keys` file in the sub-account's directory" (general page); the same key procedure works for subaccounts; a subaccount sees only its own sub-directory (its `home_directory`, a path inside the main box), the main user sees all; all subaccounts use the box's space; up to 100 per box; read-only is possible.
- Quota full: the docs say nothing (CONFIRMED absent). A restic forum report shows `sftp: "Quota exceeded" (SSH_FX_FAILURE)` at OpenFile and Rename, later `no space left on device` (https://forum.restic.net/t/mismatch-between-hetzner-disk-usage-and-restic-repository-size/9800; user-reported, one case). Snapshot data counts against the quota (general page). So an SFTP client gets `SSH_FX_FAILURE` "Quota exceeded" (INFERRED from one report); rsync/scp text unconfirmed. `df -h` on port 23 or via sftp shows the quota-based size; the Console figure updates about every 10 minutes.
- Legacy `scp -O` fails on port 22 (E17, matches Hetzner per E17 notes); not re-checked against docs.

## 4. Large dynamic VHDX

- Limit (CONFIRMED): VHDX 64 TB, VHD 2,040 GB; Gen2 SCSI: 4 controllers, 64 disks each, 256 total (https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/maximum-scale-limits). 64 TB = 64 TiB = 70368744177664 bytes; go-winio `MaximumSize` is `uint64`; the repo's `CreateDisk` takes `int64`: fits. `MaximumSize` must be >= 3 MB and a multiple of the sector size (CreateVirtualDisk remarks); block size 0 (default), 512 KB or 2 MB for `BlockSizeInBytes` per the CreateVirtualDisk page (so the default for the Win32 call is not stated there). Host volume of the file cannot be compressed or EFS-encrypted.
- Elevation: `CreateVirtualDisk` works without elevation for members of Hyper-V Administrators (repo EXPERIMENTS.md line 14, checked on this machine). Attaching goes through the Hyper-V module (`Add-VMHardDiskDrive`), which the repo already does (`internal/platform/hyperv/disks.go`, `AttachDisk`). The size is not an extra privilege (INFERRED); a 64 TiB creation was not run (UNCONFIRMED by test).
- Initial file size: a dynamic VHDX holds only header, log, metadata and the block allocation table (BAT); with a 32 MB block the BAT of 64 TiB is about 2M entries of 8 bytes (about 16 MB), INFERRED from the VHDX format (default block size not in the pages fetched, UNCONFIRMED). The host volume needs free space only for what the guest writes. The disk can be larger than the host volume.
- Guest: a disk > 2 TiB needs GPT; btrfs can use the whole device without a partition table.
- `mkfs.btrfs` (btrfs-progs 6.14): by default does a whole-device TRIM on devices that support it; `-K|--nodiscard` skips it (https://btrfs.readthedocs.io/en/latest/mkfs.btrfs.html). How long the TRIM of 64 TiB takes through Hyper-V's UNMAP handling was not found and not tested (UNCONFIRMED). Recommendation: `mkfs.btrfs -K`. Without TRIM, `mkfs.btrfs` writes only superblocks, trees and the first chunks, expected to take seconds regardless of nominal size (INFERRED).
- `btrfs quota enable`: the btrfs Qgroups page gives no duration; on an empty filesystem expected to be instant; `quota rescan` scales with used data (INFERRED). E18 rules still apply (quota on `1/<n>`, check `qgroup show` for "inconsistent", `quota rescan -w`). See section 6 for squotas.
- Practical nominal size: 64 TiB is allowed by every document read; the real limits are host free space for written data and the cost of copying a grown file (snapshots/export scale with used bytes). If a full test fails: 16 TiB or 8 TiB nominal.
- `ResizeDisk` uses `Resize-VHD` (grow only, up to 64 TB), so a smaller nominal size can be grown later.

## 5. Does trimmed space of a running dynamic VHDX return to the host (btrfs `discard=async`)?

Answer: not as a smaller file while the VM runs. UNCONFIRMED in detail; documented facts below.

- CONFIRMED (Microsoft, "Hyper-V storage I/O performance", Unmap notification integration): since Windows Server 2012 Hyper-V passes guest `unmap` to the VHDX stack "so the stack can reclaim unused storage space"; only Hyper-V SCSI, enlightened IDE and Virtual Fibre Channel controllers pass `unmap` to the host, and on VHD files only VHDX supports it. A note on the same page says trimming needs "pass-through or SCSI disks and trim-compatible hardware". The data disk is on SCSI: fine. The page does not say that the VHDX file shrinks, nor mention NTFS vs ReFS or block size for it.
- Documented host behaviour of compaction (Optimize-VHD page): the file is shrunk only by the compact operation ("reclaims unused blocks as well as rearranges blocks"), which requires the disk not attached or attached read-only (section 7). Practice reports (Helge Klein, helgeklein.com/blog/faster-trimming-compacting-hyper-v-ubuntu-vms/): `fstrim` in the Linux guest, then shut down the VM and run `Optimize-VHD -Mode Full` with the disk mounted read-only; the author says space is only freed after that ("you need to shut down the Ubuntu VM"). I found no source showing an online host-only shrink of a VHDX file. INFERRED: unmapped blocks are marked unallocated/trimmed in the VHDX BAT and reused by later guest writes (so the file stops growing for steady workloads), but file length stays until a compaction.
- Conditions: a VHDX block (default 32 MB for a CreateVirtualDisk/New-VHD VHDX is INFERRED; the New-VHD page lists no default; Microsoft's Linux page suggests 1 MB blocks for Linux VHDX) can only be dropped when every sector of it is trimmed, so btrfs free space must be contiguous at block granularity. btrfs `discard=async` (default since kernel 6.2 when the device reports discard support, INFERRED) trims freed extents in the background, with rate limits; small free fragments below the block size free nothing. A host NTFS/ReFS difference is not documented anywhere I found (UNCONFIRMED); `Optimize-VHD` does not state a file system requirement for the host.
- `Optimize-VHD` therefore IS needed to shrink the file; plan it for when the storage VM is off (section 7). `fstrim` or `discard=async` in the guest is still needed beforehand so that Quick/Retrim have something to reclaim.

## 6. btrfs simple quotas (squota) on Debian 13 (kernel 6.12, btrfs-progs 6.14)

- Availability (CONFIRMED): squota arrived in kernel 6.7 and btrfs-progs 6.7; enable with `btrfs quota enable --simple <mnt>` (btrfs-quota docs: `-s|--simple`). Debian 13 meets both (kernel 6.12.x, btrfs-progs 6.14-1; E18 ran progs 6.14). Enabling sets an incompat bit `SIMPLE_QUOTA` (older kernels, e.g. 5.15, can't mount; removing needs `btrfstune --remove-simple-quota`, progs >= 6.13) (Oracle Linux blog summary via search, LWN 938802). Squotas cannot be turned on retroactively for existing data: accounting starts at 0 and only covers extents created after enabling (Oracle guide, as of 6.13). Fine for a freshly made data disk. Do not combine with an already running full-qgroup filesystem: disable first (`quota disable`), different mode (UNCONFIRMED whether switching in place is possible; mkfs fresh to be safe).
- API: same qgroup commands (`qgroup create/assign/limit`), same hierarchy; limits are set with `btrfs qgroup limit <size> <path|qgroupid>` (btrfs-qgroup docs: limits apply per qgroup "when any limit is reached in the tree containing the subvolume"; they work only while qgroups are consistent). Whether `limit` on `0/<subvol>` and on level-1 `1/<n>` is enforced under squotas: the sources say squotas "reuse the qgroups API" and "add automatic inheritance for nested subvolumes" (LWN), so level-0 limits are expected to work; a level-1 limit over several subvolumes is plausible but NOT confirmed anywhere. UNCONFIRMED: must be probed on a 6.12 guest before phase 20 relies on it (limit on `0/<home>` and on `1/<n>`, write until `EDQUOT`).
- Accounting difference (CONFIRMED, LWN 938802, btrfs Qgroups page): squotas "account all extents permanently to the subvolume in which they were originally created". They do not distinguish shared from exclusive (exclusive == shared == referenced per qgroup). Consequences for E18/phase 20:
  - A read-only snapshot taken with `-r` is a new subvolume with ~0 own charge; the shared data stays charged to the original `home`. Writes after the snapshot create new extents charged to `home`; deleting the file in `home` leaves the old extents charged to `home` while the snapshot still references them (the Qgroups page example: after emptying 256, 512 MiB stay charged to 256). So "snapshot data counts against the limit" still holds, as in E18, but it is charged to the original owner, and not the snapshot.
  - Rollback (E18: `mv home home.old`, writable snapshot of the snapshot as new `home`, delete `home.old`): the new `home` owns nothing, so its limit would allow a whole new box's size on top of the data referenced from the snapshot; the old extents stay charged to the (deleted) `home.old`'s qgroup as long as any snapshot references them, and then disappear. A deleted subvolume may keep its accounting (btrfs-qgroup docs, simple mode: "a fully deleted subvolume may still carry accounting"). Net: after a rollback the box can use up to limit plus the snapshot data; need an explicit design (quota on a level-1 qgroup `1/<n>` to which old and new subvolumes are assigned, or accept the slack). UNCONFIRMED how `-i 1/<n>` inheritance behaves under squotas.
  - `stats` for a box: the "referenced/exclusive" numbers from `qgroup show --raw` are the same under squotas (excl == rfer), so per-snapshot exclusive sizes cannot be shown.
- Performance (CONFIRMED qualitatively): squotas never compute global reference counts, so accounting is local to allocation/free and performance is close to quotas disabled, while full qgroups cause commit latency and write-bandwidth regressions as snapshots accumulate (LWN: author's benchmark; he also noted an open squota umount regression in 2023, status unknown for 6.12).
- Pitfalls: no retroactive accounting; incompat bit; shared/exclusive not separable; limit after owner deletion or rollback as above; `quota rescan` is for full qgroups (squota numbers cannot be rebuilt by rescan: INFERRED, since accounting is stored in extent items; UNCONFIRMED); E18's "inconsistent" problem is a full-qgroup phenomenon and is not expected under squotas (INFERRED).
- Recommendation: keep E18's full qgroups (tested, rollback semantics known) unless a probe on 6.12 shows squota limits enforce on `0/<home>` / `1/<n>` and the rollback slack is acceptable; squota is the better fit only if many snapshots make full qgroups slow.

## 7. `Optimize-VHD` on a detached dynamic VHDX

Source: https://learn.microsoft.com/en-us/powershell/module/hyper-v/optimize-vhd (CONFIRMED).
- Requirements: Hyper-V PowerShell module (Hyper-V role feature "Hyper-V Module for Windows PowerShell"); "the virtual hard disk must not be attached or must be attached in read-only mode"; works on dynamic and differencing disks, not fixed.
- Modes: default for VHDX is `Quick`. `Full` scans for zero blocks and reclaims unused blocks, allowed only if the disk is mounted read-only; `Quick` reclaims unused blocks without scanning zeros, also only read-only mounted; `Retrim` sends retrims without scanning or reclaiming, read-only mounted only (error otherwise); `Pretrimmed` = Quick without the read-only mount but "less effective" because it cannot query NTFS free space; `Prezeroed` = Quick without read-only mount, reclaiming blocks that are all zero (explicitly "useful in handling virtual hard disks containing file systems other than NTFS"). The page's examples: `-Mode Full` on a disk not attached read-only "will default to Prezeroed"; `-Mode Quick` not attached read-only "defaults to Pretrimmed"; `-Mode Retrim` not read-only mounted returns an error.
- So on a merely detached (not mounted) VHDX: `Full` runs as `Prezeroed`, `Quick` as `Pretrimmed`. Non-NTFS guests (btrfs): the host cannot read btrfs free space even with a read-only mount, so the NTFS-aware part of `Full`/`Quick` gives nothing; reclaim then relies on (a) blocks that were unmapped by guest TRIM (`Pretrimmed`/`Quick` handle trimmed blocks) and (b) blocks that are entirely zero (`Prezeroed`/`Full` scan, which reads all allocated blocks: slow on a big disk). A `Full` scan of a mostly empty disk costs about the allocated size in reads (INFERRED; duration not documented, Helge Klein reports "a few minutes" for a 103 GB to 31 GB case with trim first).
- Recommended for btrfs: run `fstrim -av` (or rely on `discard=async`) in the guest, stop the VM, then `Optimize-VHD -Path x.vhdx -Mode Pretrimmed` (detached; cheap) and optionally `Prezeroed` afterwards. Whether `Retrim` helps is unclear (it needs a read-only mount).
- Elevation: UNCONFIRMED. The docs state no privilege. Detached `Optimize-VHD` goes through the Hyper-V management service (VHD service), whose access is granted to Hyper-V Administrators like `New-VHD`/`Resize-VHD`, so it is expected to work unelevated for that group (INFERRED, same path as `Convert-VHD`/`Set-VHD` already used in `disks.go`). A read-only mount (`Mount-VHD -ReadOnly`) attaches the disk to the host's storage stack and is expected to need elevation or SeManageVolumePrivilege (UNCONFIRMED, not tested here). Avoid needing it by using `Pretrimmed`/`Prezeroed`.
- The VM must be off (Hyper-V locks the VHDX while a VM uses it; hlab's storage VM stops with the cloud, so the optimisation fits a "stop" hook, duration unknown).

## 8. Free space of a host folder's drive from Go on Windows (no elevation)

- `GetDiskFreeSpaceExW(lpDirectoryName, lpFreeBytesAvailableToCaller, lpTotalNumberOfBytes, lpTotalNumberOfFreeBytes)` in kernel32 (https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdiskfreespaceexw): any directory on the drive is accepted (not only the root); the caller needs `FILE_LIST_DIRECTORY` access to that directory (no administrator right); a UNC path needs a trailing backslash; a symbolic link is followed to its target; with per-user quotas the "available to caller" and total values can be smaller than the real ones (use `lpTotalNumberOfFreeBytes` for the drive's free space); values are 64-bit.
- Go: `golang.org/x/sys/windows` v0.50.0 (the version in SPEC.md) has `func GetDiskFreeSpaceEx(directoryName *uint16, freeBytesAvailableToCaller *uint64, totalNumberOfBytes *uint64, totalNumberOfFreeBytes *uint64) (err error)` (CONFIRMED in the module cache, `windows/zsyscall_windows.go`). Example: `p, _ := windows.UTF16PtrFromString(dir); var avail, total, free uint64; err := windows.GetDiskFreeSpaceEx(p, &avail, &total, &free)`; use `free` for the drive, `avail` for what the hlabd account may use.
- Pitfall: the data folder must exist (or ask for its parent); a mount-point folder on another volume reports that volume's numbers (the target is what counts, per the symlink remark; mount-point behaviour itself is not stated, INFERRED). The free space of the host is not reduced by the nominal size of a dynamic VHDX, so a 64 TiB disk on a small drive can run the host volume out of space when the guest writes; hlab should check `free` before accepting writes (a box create) rather than at disk creation.
