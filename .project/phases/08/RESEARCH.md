### 1.2 Runtime API (per-LB instance)

Config: `stats socket /run/hlab/lb<ID>.sock mode 600 level operator` in `global` (a unix socket is a filesystem object, so the agent in the root namespace reaches an HAProxy running inside the LB's netns). Commands are plain text lines, one per connection (the socket closes after a command unless `prompt`/`;` chaining is used).

- Health per backend and server: `show stat <iid|proxy> 4 -1` or simply `show stat` and filter. Full syntax (HAPROXY management 9.3): `show stat [domain <resolvers|proxy>] [{<iid>|<proxy>} <type> <sid>] [typed|json] [desc] [up|no-maint]`; `<type>` 1 = frontends, 2 = backends, 4 = servers, -1 = all (ORable), `<sid>` -1 = everything of the proxy. CSV with a `# ` header line. Columns by index: 0 pxname, 1 svname, 2 qcur, 4 scur, 7 stot, 8 bin, 9 bout, 17 status, 18 weight, 21 chkfail, 22 chkdown, 23 lastchg, 32 type (0 frontend, 1 backend, 2 server), 36 check_status, 37 check_code, 38 check_duration, 48 req_tot, 73 addr. Server `status` is `UP`/`DOWN`/`NOLB`/`MAINT`/`MAINT(via)`/`MAINT(resolution)`; INFERRED from HAProxy source (not in the fetched docs): while the check counters are mid-transition the CSV shows `UP 1/3` or `DOWN 1/2`, so parse the first token. `check_status` values: UNK, INI, SOCKERR, L4OK, L4TOUT, L4CON, L6OK, L6TOUT, L6RSP, L7OK, L7OKC, L7TOUT, L7RSP, L7STS. Mapping to Hetzner `health_status.status`: INI/UNK before the first completed check = `unknown`; UP = `healthy`; DOWN = `unhealthy` (detail: SOCKERR/L4CON -> layer4_no_connection, L4TOUT -> layer4_timeout, L7TOUT -> layer7_timeout, L7STS -> unexpected_http_status with `check_code`; body mismatch -> unexpected_http_content: which check_status HAProxy reports for a failed `expect string` is UNCONFIRMED).
- Alternative: `show servers state [<backend>]` (format version 1, `#` header; fields be_id, be_name, srv_id, srv_name, srv_addr, srv_op_state 0 stopped/1 starting/2 running/3 stopping, srv_admin_state bitmask, srv_uweight, srv_iweight, srv_check_status, srv_check_result, srv_port ...) is meant for saving state, not for counters; use `show stat`.
- Counters per LB: sum over FRONTEND rows (type 0): `scur` = open connections, `stot` = sessions (connections) total, `req_tot` = requests total (only counted for mode http frontends; a tcp frontend reports 0, INFERRED), `bin`/`bout` = bytes in/out. `show info` has CurrConns, CumConns, CumReq (names from the docs' example output) but covers the whole process.
- Pitfall: counters belong to the worker process and restart at 0 after a reload; treat a smaller value than the last sample as a reset and add the new value (the old worker's last seconds are lost). Hetzner's metrics are rates (connections_per_second etc.): derive from deltas of consecutive samples.
- Pitfall: server health also restarts after a reload. Keep it with `server-state-file` plus `load-server-state-from-file global` (dump with `show servers state` before reload) or accept `unknown` for one check interval; INFERRED, not tested.

### 1.3 Reload in master-worker mode

Start each instance as `ip netns exec lb<ID> haproxy -W -f /run/hlab/lb<ID>/haproxy.cfg -S /run/hlab/lb<ID>/master.sock,level admin -p <pidfile>` (no `-D`, so the agent supervises). Documented behaviour (HAPROXY management 4): the master reacts to SIGUSR2 by re-executing itself with `-sf <worker pids>`, parses the config, forks new workers, the old ones finish their connections and leave; `-S` binds the master CLI ("recommended to bind to a local UNIX socket"); in master-worker mode `-x`/`expose-fd listeners` are not needed because the master uses `sockpair@` automatically. The master CLI has a synchronous `reload` command ("will return a reload status once the reload was performed", documented in the 3.0 guide) and `show proc`. Practical sequence: write the new cfg and certs, `haproxy -c -f <cfg>` (a bad config must not reach the running master: a failed reload keeps the old workers), then `echo reload | socat - UNIX-CONNECT:master.sock` (socat is in the image) or send a Go `net.Dial("unix")` line; read the status text; on failure keep the old generation and report. `mworker-max-reloads` was not found in the fetched text (UNCONFIRMED). The re-exec uses the original argv: give absolute paths and keep the binary path stable.
- The netns is only needed at start; a reload re-executes inside the same namespace.

### 1.4 Config mapping notes (INFERRED from the 3.0 configuration manual; verify in the unit tests with `haproxy -c`)

- Health check, http: `option httpchk`, `http-check connect [ssl sni <domain>]`, `http-check send meth GET uri <path> ver HTTP/1.1 hdr Host <domain>` (documented: `ver` defaults to HTTP/1.0, 1.1 needs the Host header added by hand; `uri` defaults to `/`; `meth` defaults to OPTIONS), `http-check expect rstatus <regex>`; status patterns `2??` / `*` become regex (`?` -> `.`, `*` -> `.*`), several patterns -> one alternation `^(2..|3..)$`. Hetzner `response` (string contained in the response) maps to `http-check expect string <s>` / `rstring`; the manual excerpt does not state whether two `expect` rules in one ruleset must both match (UNCONFIRMED; test it). `fall <retries> rise <retries> inter <interval>s` and `timeout check <timeout>s` match Hetzner's "an unhealthy target needs the same number of successful retries to become healthy again" (OPENAPI add_service).
- PROXY protocol: HAProxy `send-proxy` = v1 text, `send-proxy-v2` = binary v2. Which version Hetzner sends is UNCONFIRMED (section 3).
- Sticky cookie: `cookie <name> insert indirect nocache` with a lifetime via `maxlife`/`attr "Max-Age=<s>"`: the exact cookie attributes Hetzner sets are UNCONFIRMED.
- TLS: `bind :443 ssl crt <dir or file(s)>`; the first certificate is the default, others are chosen by SNI. Concatenate leaf, chain and key into one PEM per certificate.
- HAProxy ignores a stale unix socket file at start: remove it first.

## 2. Network design for the netns per LB (no experiment possible without a shell; unverified)

Existing facts from the repo: the firewall applier (`internal/agent/firewall_linux.go`) hooks `forward` at filter+10 and matches only `oifname <pub> ip daddr <server addr>` (inbound rules) and `iifname <pub> ip saddr <server addr>` (outbound rules); the isolation table (`isolation_linux.go`) puts `iifname t<vlan>` into conntrack zone `<vlan>` in a raw-priority prerouting chain and drops forwarded packets from known member MACs with foreign sources. Private networks are `vrf<vlan>` (table 1000+vlan) with the VLAN subinterface `t<vlan>` enslaved, gateway = network address .1 as /32.

Design (a) public targets: veth pair `lbp<ID>` (root) / `eth0` (netns). Netns side: LB public IPv4 as /32 (and nothing else), a /31 or /30 transit address from a reserved block that cannot clash with user ranges (169.254.0.0/16 except 169.254.169.254, or a CGNAT block), `default via <root end>`. Root side: transit address, `ip route add <LB public IPv4>/32 dev lbp<ID>`, `net.ipv4.ip_forward=1` is already on. Client -> LB: arrives on the public NIC, forwarded to the veth (oif is the veth, so the firewall's `oifname <pub>` rules do not match: LB inbound is not filtered, as at Hetzner). LB -> public target: leaves the netns with the LB public IP as source, root forwards it out the public NIC, `oifname <pub> ip daddr <target>` matches, so the target server's inbound firewall applies with the LB's IP as source (Hetzner behaves the same: the LB's address must be allowed). Health checks take the same path. Return traffic: target replies to the LB public /32, the appliance routes it to the veth; the `ct state established,related accept` rule at the top of `forward` (present when any firewall exists) passes it. The isolation drop for guest MACs does not touch it (source is the LB's, MAC is the appliance's). Alternative to numbered transit: unnumbered veth + `proxy_arp=1` on the root end; numbered is more deterministic.

Design (b) private targets: per (LB, network) a second veth; the root end is enslaved to `vrf<vlan>` (`ip link set lbn<ID>_<vlan> master vrf<vlan>`), the netns end carries the LB's private IP (from `LBNetwork.IP`) as /32 plus a transit address; netns route `<network range> via <root end transit> dev <veth> src <LB private IP>`; VRF table route `<LB private IP>/32 dev <veth>` (table 1000+vlan, with the agent's route protocol so the VRF applier's cleanup does not drop it or, better, let the VRF applier own it). Targets reply to the network gateway (their route to the range goes via the gateway /32), the VRF looks up `<LB IP>/32` and sends it to the veth. Risks:
1. Conntrack zone mismatch: only `iifname t<vlan>` is put into zone `<vlan>`. Packets entering from the veth would be tracked in zone 0 and the replies (from `t<vlan>`) in zone `<vlan>`, so they never match the same entry. Fix: add `iifname <veth> ct zone set <vlan>` in the same raw chain for every LB veth in a network. Stateless forwarding still works without it (the table policy is accept), but stateful rules would not.
2. `rp_filter` strict mode in the VRF: the routes above make the reverse path consistent; check with `ip route get <LB IP> from <target IP> iif t<vlan> vrf vrf<vlan>`.
3. The isolation set `member_sources` drops forwarded packets from member MACs with foreign sources: the LB's address is never source from a member MAC, fine. Members must route to the LB IP through the gateway: their route to the range via the gateway covers it (Hetzner puts the LB inside the network range).
4. Overlapping ranges between projects are separated by the VRFs; one LB netns only gets veths into its own project's networks.
5. Several LBs with the same private IP in different VRFs are fine; the netns holds each LB only once.
6. HAProxy binds `0.0.0.0:<listen_port>` inside the netns, so it answers on the public and every private LB address; `public_net.enabled=false` means removing the public veth/address, not changing the config.
7. `use_private_ip` targets and `disable_public_interface`: Hetzner refuses disable while a target uses the public IP (`targets_without_use_private_ip`, section 3).
8. ICMP and MTU: veth MTU 1500, same as the trunk (Hyper-V VLAN subinterface; no jumbo frames configured elsewhere).
Netns lifecycle: create with `ip netns add lb<ID>` (or netlink + `netns.NewNamed`); delete the HAProxy first, then `ip netns del`, then veth ends disappear with it. All of this must be idempotent from `agentapi.Config`, like the VRF applier.

Not covered by EXPERIMENTS.md E1-E11 and not run in this session. Suggested first e2e probe before the plan is finalised: one netns with design (a), curl from the host to the LB public IP and from the LB netns to a server's public IP, with and without an inbound firewall on the target; then design (b) with `conntrack -L` to see both directions in one zone.

## 3. Hetzner Cloud load balancer behaviour

### 3.1 Service fields and defaults
- Service: `protocol` tcp|http|https, `listen_port`, `destination_port`, `proxyprotocol` (bool), `http` (not for tcp), `health_check`. In the add_service request the spec lists `protocol`, `listen_port`, `destination_port`, `proxyprotocol`, `health_check` as required, and inside it `protocol`, `port`, `interval`, `timeout`, `retries`; no defaults are given for those. The hcloud CLI sends `health_check` only when a `--health-check-*` flag was given and Terraform only when the block is set, so real clients may omit it: what the API then does (default health check or `invalid_input`) is UNCONFIRMED. Plan: accept an omitted health_check and default to tcp on the destination port, interval 15, timeout 10, retries 3 (the CLI flag defaults), and mark it a guess.
- http defaults: `cookie_name` HCLBSTICKY (1-100 chars), `cookie_lifetime` 300 (30-86400), `sticky_sessions` false, `redirect_http` false (https only), `timeout_idle` 50 (30-300), `certificates` IDs (HTTPS: terminate TLS; empty list = passthrough "or if protocol is http"; description text truncated in the spec).
- health_check: `interval` 3-60 (example 15), `timeout` 1-60 (example 10), `retries` 1-5 (example 3), protocol enum `tcp`,`http` in the spec; the Ansible docs also list `https`, TF docs say http|https|tcp: UNCONFIRMED whether the API accepts `https` as health protocol (the spec expresses HTTPS with `http.tls: true`). `http.domain` max 128, nullable (null = no Host header), `http.path` 1-256, `http.response` max 256, `http.status_codes` default `["2??","3??"]`, max 20 items, "Supports the wildcards `?` for exactly one character and `*` for multiple ones", `http.tls` bool.
- Type limits (`load_balancer_type`): `max_services`, `max_targets`, `max_assigned_certificates`, `max_connections`; lb11 = 10,000 connections, 5 services, 25 targets, 10 certificates (docs.hetzner.com load-balancers overview). The error returned when a limit is exceeded is UNCONFIRMED (no code in the spec; candidates `invalid_input` or `resource_limit_exceeded`).
- Forwarded headers for http/https services: X-Forwarded-For, X-Forwarded-Proto, X-Forwarded-Port (FAQ); not added for tcp.
- Health status per target: `health_status[]` with `listen_port`, `status` healthy|unhealthy|unknown, `detail` (only when unhealthy) unspecified|layer4_no_connection|layer4_timeout|layer7_timeout|unexpected_http_status|unexpected_http_content, `http_status_code` (only for unexpected_http_status). Present only for targets of type server and ip (a label_selector target carries nested `targets[]` with their own health_status).
- Targets: `type` server|label_selector|ip; `use_private_ip` for server and label_selector only; hcloud-go response `Targets[].{Server.ID | LabelSelector.Selector | IP.IP, HealthStatus, Targets, UsePrivateIP}`.

### 3.3 redirect_http and port 80
OPENAPI: "Redirect HTTP requests to HTTPS. Only available if `protocol` is `https`." Terraform docs: "Only supported for services with `protocol` `https` using the default HTTP port `80`" (my reading: the redirect listens on port 80). Ansible: "Redirect Traffic from Port 80 to Port 443". No document states that another service on port 80 is refused. INFERRED rule: with `redirect_http=true` port 80 is taken by the redirect, so a second service with listen_port 80 fails with `source_port_already_used` (412 on add_service, 422 on update_service per the spec tables), and enabling the redirect while a service already uses 80 should fail the same way. Unproven against the API: probe it. Also Hetzner ties the redirect to the https service on port 443 only per the TF text: whether `listen_port` != 443 with redirect_http is allowed is UNCONFIRMED. Sending `redirect_http: false` for a plain http service must be accepted (the CLI always sends `redirect_http` and `sticky_sessions` for http and https).

### 3.5 Metrics (GET /load_balancers/{id}/metrics)
- Query: `type` (required, one or several comma-separated: `open_connections`, `connections_per_second`, `requests_per_second`, `bandwidth`), `start` and `end` (required, RFC3339), `step` (optional, "Resolution of results in seconds", schema type string).
- Series names in `time_series`: `open_connections` (number), `connections_per_second`, `requests_per_second`, `bandwidth.in` and `bandwidth.out` (bytes/s).
- Rules: last 30 days only; default step chosen so that 200 samples are returned; at most 500 samples (step adjusted up).
- Response: `{"metrics":{"start":"2017-01-01T00:00:00Z","end":"2017-01-01T23:00:00Z","step":60,"time_series":{"<name>":{"values":[[1435781470.622,"42"],[1435781471.622,"43"]]}}}}`: timestamp is a float (Unix seconds), value is a string; hcloud-go `LoadBalancerMetrics{Start,End,Step float64,TimeSeries map[string][]{Timestamp float64,Value string}}`.

### 3.6 Action and client waiting
All LB mutations return an action (`add_service`, `add_target`, `attach_to_network`, ...), HTTP 201. hcloud-go `WaitFor` polls `GET /actions?id=<id>&id=...&sort=status&sort=id` (chunks of 25; the per-resource `GET /load_balancers/{id}/actions/{id}` is deprecated), stops on any status other than `running`, returns an `ActionError` for `error`, and fails with "actions not found" if an ID is missing in the answer. No timeout of its own.

## 4. Hetzner certificate behaviour

- Create managed: `POST /certificates` with `type: managed`, `domain_names`; the response carries `action` (command `create_certificate`) and the certificate with `status: {"issuance":"pending","renewal":"unavailable","error":null}` (spec example). Schema example for a finished one: issuance `completed`, renewal `scheduled`. Values: issuance pending|completed|failed; renewal scheduled|pending|failed|unavailable; `status` is `null` for uploaded certificates; `error` is `{code,message}` "if issuance or renewal reports failed". "Only domains managed by Hetzner DNS are supported."
- Domain not in Hetzner DNS: the spec does not give the exact code/message. Codes the retry operation lists (and hcloud-go has): `dns_zone_not_found`, `dns_zone_is_secondary_zone`, `could_not_verify_domain_delegated_to_zone`, `caa_record_does_not_allow_ca`, `ca_dns_validation_failed`, `ca_too_many_authorizations_failed_recently`, `ca_too_many_certificates_issued_for_registered_domain`, `ca_too_many_duplicate_certificates` (messages like "DNS zone not found", "Could not verify domain delegated to zone"). INFERRED: a domain without a zone ends as issuance `failed` with `status.error.code = "dns_zone_not_found"`; the failed action's `error` is the generic `{"code":"action_failed","message":"Action failed"}` (the spec's action example): UNCONFIRMED whether the action error carries the specific code. hlab decision as in decisions/managed-certificates.md; use `dns_zone_not_found` and message "DNS zone not found" unless a probe says otherwise.
- Retry: `POST /certificates/{id}/actions/retry`, "Only applicable if the type of the Certificate is `managed` and the issuance or renewal status is `failed`", 201 + Action. The answer for a non-failed or uploaded certificate is not documented (no error table row): UNCONFIRMED; suggest 422 `invalid_input`-style refusal... clearly flag it as a guess; hlab may use code `unsupported_error` or `invalid_input`.
- Delete: `DELETE /certificates/{id}` -> 204. The spec has no error table for delete. A third-party MCP description says it "must not be in use by any load balancer"; hcloud-go has `resource_in_use` ("Firewall in use and can't be deleted"), so INFERRED: 422 `resource_in_use`. UNCONFIRMED. `used_by` is `[{"id":4711,"type":"load_balancer"}]`. Terraform's delete does not retry or wait.
- Renewal timing: "We handle renewal and timely alert the project owner via email" and FAQ "automatically renewed"; no timing stated. Let's Encrypt style (90 days, renew at 30 days left) is a reasonable hlab choice.
- Uploaded: `certificate` "Certificate and chain in PEM format, in order so that each record directly certifies the one preceding", `private_key` PEM. The spec and FAQ ("You will have to monitor its expiration date") state no expiry or chain-order validation on upload; whether the API rejects an expired certificate or a mis-ordered chain is UNCONFIRMED (error code for invalid PEM/key mismatch likely `invalid_input`). Fields read from it: `fingerprint` (SHA256 of the certificate), `not_valid_before`, `not_valid_after`, `domain_names`.
- Update: only `name` and `labels`; "if the Certificate object changes during the request, the response will be a conflict error".

## 5. Client behaviour (hcloud CLI v1.70.2, provider hcloud v1.70.2, Ansible hetzner.hcloud 7.2.0)

hcloud CLI (waits through `s.WaitForActions`, i.e. hcloud-go polling above, one action per call):
- `load-balancer create`: sends `name`, `load_balancer_type`, optional `algorithm`, `location` or `network_zone`, `network`, `public_net` primary IPs, `labels`; waits only for the create action (not `next_actions`); then `GET /load_balancers/{id}` and prints `PublicNet.IPv4.IP` and IPv6 without nil checks, so both `public_net.ipv4.ip` and `ipv6.ip` should be present in the response.
- `add-service`: always sends `protocol` and `proxyprotocol`; `listen_port`/`destination_port` when non-zero; for http/https `http.sticky_sessions` and `http.redirect_http` always, `cookie_name`, `cookie_lifetime`, `timeout_idle` only when non-zero, `certificates` as IDs after resolving each by name/ID (`GET /certificates`); `health_check` only when a `--health-check-*` flag was set (then protocol and port are mandatory, interval/timeout/retries only if given, http sub-object only for http/https with domain/path/response/status_codes/tls only if given). No refetch afterwards.
- `add-target`: `--server` -> `{type:server, server:{id}, use_private_ip}`, `--label-selector` -> `{type:label_selector, label_selector:{selector}, use_private_ip}`, `--ip` -> `{type:ip, ip:{ip}}` (no use_private_ip). One action, waited.
- `certificate create --type managed` waits for the create action (error if it fails); decisions/managed-certificates.md has the rest.

OpenTofu hcloud 1.70.2:
- `hcloud_load_balancer`: create sends name, type, optional algorithm/location/network_zone/labels/targets/primary IPs; waits only for the create action; ID set before the wait; read uses `ipv4`, `ipv6`, `location.name`, `location.network_zone`, `algorithm`, `private_net` (network_id, network_ip), targets (server targets only).
- `hcloud_load_balancer_network`: `attach_to_network` (`network`, optional `ip`/`ip_range`) with retry on conflict, locked, service_error and `no_subnet_available`; tolerates `load_balancer_already_attached`; waits; refetches and needs `private_net[]` with `network` and `ip` for that network ("Resource vanished" otherwise); `enable_public_interface` default true: calls enable/disable only when different from `public_net.enabled`; on delete detach with retries, then polls up to 10 x 2 s until `private_net` no longer lists the network.
- `hcloud_load_balancer_service`: ID `<lb_id>__<listen_port>`; every operation first `GET /load_balancers/{id}` and finds the service by `listen_port` (a failing GET removes the resource from state); create defaults listen_port to 80 (http) or 443 (https); sends destination_port, proxyprotocol, http, health_check only when set; retries only on `service_error`; update always sends `protocol` and `proxyprotocol`, and `cookie_name`/`cookie_lifetime` when the keys exist, even empty or zero (so an update with `cookie_lifetime: 0` must not fail validation); read needs `services[].http` for non-tcp services (it writes `redirect_http` always, `certificates[].id`, cookie fields only when non-zero) and `health_check` (`retries` only if > 0, `http` block only if present, always `tls` and `status_codes`).
- `hcloud_load_balancer_target`: add server/label_selector/ip target; for `use_private_ip=true` it first checks client-side that the LB has `private_net`; treats `target_already_defined` as success; read scans `targets[]` by `server.id`, `label_selector.selector`, `ip.ip` and reads `use_private_ip`; remove retried on conflict/locked, tolerates "not found"; update = remove + add. It does not read `health_status`.
- `hcloud_managed_certificate`/`hcloud_uploaded_certificate` (provider `internal/certificate/resource.go`): managed create sends `name`, `type: managed`, `domain_names`; ID set, then `WaitFor(create action)`: a failed issuance makes apply fail but the ID is already in state; read does not evaluate `status`; uploaded create sends `certificate`, `private_key` and needs no action (action absent/empty); update only `name`, `labels`; delete does not wait and does not retry `resource_in_use`.

Ansible hetzner.hcloud 7.2.0:
- `load_balancer_service`: finds the service by `listen_port` in `GET /load_balancers/{id}`; create always sends protocol, listen_port, proxyprotocol (default false) and adds destination_port/http/health_check when truthy; update sends only differing fields; module defaults `sticky_sessions`, `redirect_http`, `health_check.http.tls` = false are compared on every run, so `GET` must echo them (booleans, not null); certificates compared as sorted ID lists; waits with `action.wait_until_finished()` (library default).

## 6. Windows trust store from the SYSTEM service

- Adding a root to `LocalMachine\Root` needs administrator rights, which SYSTEM has, and shows no prompt; the "Security Warning" dialog is the CurrentUser\Root path (community answers; Microsoft docs only state `certutil -f -addstore root file.cer` from an elevated prompt installs for all users). UNCONFIRMED on this build (10.0.26300) because nothing was run; verify in the first CERT-04 e2e run.
- x/sys/windows v0.50.0 (the version in go.mod) has what is needed, except `CertAddEncodedCertificateToStore` (not wrapped): `CertOpenStore(windows.CERT_STORE_PROV_SYSTEM, 0, 0, windows.CERT_SYSTEM_STORE_LOCAL_MACHINE, uintptr(unsafe.Pointer(windows.StringToUTF16Ptr("ROOT"))))`; `CertCreateCertificateContext(windows.X509_ASN_ENCODING, &der[0], len)` then `CertAddCertificateContextToStore(store, ctx, windows.CERT_STORE_ADD_REPLACE_EXISTING, nil)`; remove with `CertFindCertificateInStore(store, windows.X509_ASN_ENCODING, 0, windows.CERT_FIND_SHA1_HASH, unsafe.Pointer(&windows.CryptHashBlob{Size: 20, Data: &sha1[0]}), nil)` (SHA-1 thumbprint of the DER) and `CertDeleteCertificateFromStore(ctx)` (it frees the context: do not call CertFreeCertificateContext on it afterwards); free the other contexts and `CertCloseStore(store, 0)`. Also present: `CertEnumCertificatesInStore`. The store name "ROOT" is Trusted Root Certification Authorities. PowerShell alternative: `Import-Certificate -FilePath ... -CertStoreLocation Cert:\LocalMachine\Root` / `certutil -addstore -f Root` / `Remove-Item Cert:\LocalMachine\Root\<thumbprint>`; the project runs hlabd's PowerShell as a persistent process, but the Go calls avoid text parsing and localisation issues (see EXPERIMENTS.md E2 on localised output).
- curl.exe: Windows' curl is built with Schannel and "uses the Windows native CA store for verification" (curl docs, sslcerts); a root in LocalMachine\Root is trusted without further setup (no cache or restart expected; UNCONFIRMED on this machine).
- MAIN RISK for success criterion 2: Schannel in curl runs revocation checks by default ("Schannel runs CRL checks on certificates unless peer verification is disabled", curl docs). A leaf certificate without a CRL distribution point or OCSP URL typically fails in curl.exe with `CRYPT_E_NO_REVOCATION_CHECK (0x80092012)` ("The revocation function was unable to check revocation"); this is widely reported for private CAs and self-signed certificates and is bypassed only by `--ssl-no-revoke` (or `--ssl-revoke-best-effort`). Not tested here; I found no source that confirms or refutes it for a private root with a leaf lacking CDP. Two ways out, both unverified: (1) put a CRL Distribution Point extension into every issued leaf, pointing at a URL hlab serves (for example `http://api.hetzner.internal/...ca.crl`, reachable through the appliance's port-80 proxy) and publish an empty, regularly refreshed CRL signed by the CA; (2) make tests and docs use `--ssl-no-revoke` (weakens the claim "curl https://<name> succeeds"). Check this first in the CERT-04 e2e test; Go clients, browsers via Schannel/CryptoAPI with default policy behave differently (Chromium treats missing revocation info as soft-fail).
- Also note: leaf certificates need `subjectAltName` DNS entries (CN alone is rejected), `extendedKeyUsage serverAuth`, and a validity within what browsers/Schannel accept; the CA needs `basicConstraints CA:true`, `keyUsage keyCertSign,cRLSign`.

## 7. WSL trust from the SYSTEM service

- WSL distros are registered per user (HKCU Lxss), so `wsl.exe` run as SYSTEM sees no user distros (INFERRED from discussions, e.g. an Intune report that `wsl --install` under SYSTEM does nothing; a Q&A thread reports a scheduled task running wsl.exe as SYSTEM, Local Service or a domain account failed with 0x80070001: https://learn.microsoft.com/en-us/answers/questions/1184579/unable-to-start-wsl-from-a-scheduled-task). The WSL service itself runs as Local System (maintainer statement in microsoft/WSL#11894) and the WSL 2 VM and distros are started per user session.
- Starting wsl.exe with the console user's token: `WTSGetActiveConsoleSessionId` (or `WTSEnumerateSessions`, to pick an active session), `WTSQueryUserToken(session)` ("obtains the primary access token of the logged-on user ... the calling application must be running within the context of the LocalSystem account and have the SE_TCB_NAME privilege", Microsoft docs), `CreateEnvironmentBlock`, `CreateProcessAsUser` with `CREATE_NO_WINDOW | CREATE_UNICODE_ENVIRONMENT`, desktop `winsta0\default`. All of these exist in x/sys/windows v0.50.0 (`WTSQueryUserToken`, `WTSEnumerateSessions`, `WTSGetActiveConsoleSessionId`, `CreateProcessAsUser`, `DuplicateTokenEx`, `CreateEnvironmentBlock`). The repo already uses `xwin.WTSQueryUserToken` in `internal/hostnet/windows/wslconfig.go` (reads the console user's `.wslconfig`), so the session lookup and profile directory code exist. Because the token carries the user's session ID, the child runs in the user's interactive session, not in session 0: that is the reason it should behave like the user starting wsl.exe from a hidden window. Whether wsl.exe works that way from a service has not been confirmed anywhere I could reach: UNCONFIRMED, must be tried on this machine (list distros, run a `-u root` command, with the distro stopped).
- Commands (from the WSL docs and `wsl --help`): `wsl.exe --list --quiet` (names; add `--running` for running ones); output is UTF-16LE unless the environment variable `WSL_UTF8=1` is set (opt-in since WSL 0.64, exact value 1 only; community sources), so set `WSL_UTF8=1` in the environment block and still tolerate a UTF-16 BOM; skip `docker-desktop` and `docker-desktop-data`. `wsl.exe --distribution <name> --user root --exec <cmd>` (`-d`, `-u`, `-e`): `--exec` and `--` are in `wsl --help`, not on the "basic commands" page: UNCONFIRMED here. Pass the PEM on stdin, for example `wsl.exe -d X -u root -e sh -c 'cat > /usr/local/share/ca-certificates/hlab-ca.crt && update-ca-certificates'`, to avoid quoting problems.
- Stopped distro: running a command starts it (and the WSL 2 utility VM if it is not running); defaults: a distro stops 15 s after its last process (`instanceIdleTimeout` 15000 ms) and the VM after 60 s (`vmIdleTimeout` 60000 ms), per Microsoft's wsl-config page. The certificate persists in the distro's disk, so starting once is enough. Side effect: turning the switch on starts every distro briefly (and starts the WSL 2 VM), and every start restarts WSL's network setup that hostnet touches (E4 note about forwarding); document it, or limit to running distros plus "apply on next start".
- No user logged on: `WTSQueryUserToken` fails (documented as failing for sessions without a logged-on user; the concrete error `ERROR_NO_TOKEN` 1008 is INFERRED). Then no distro can be reached: keep the switch state, mark WSL as pending, and re-apply on the next logon (the service can receive `SERVICE_CONTROL_SESSIONCHANGE` / `WTS_SESSION_LOGON` if it registers for session notifications) or on the next trust-switch toggle. Disconnected sessions still have a token.
- Alternative through a scheduled task in the user's context (principal = the console user's SID, `LogonType InteractiveToken`, `RunLevel Limited`, `schtasks /run`): needs the user logged on as well, adds a persistent object that must be removed on uninstall, and the Microsoft Q&A above shows scheduled tasks starting wsl.exe failing in some setups. Prefer the token approach and keep the task as fallback only if the token approach fails in the test.
- CA placement on Ubuntu 24.04 (and Debian): file must be PEM with extension `.crt` below `/usr/local/share/ca-certificates/` ("Certificates must be in PEM format and have a .crt extension in order to be included by update-ca-certificates", Ubuntu noble manpage), so `/usr/local/share/ca-certificates/hlab-ca.crt` then `update-ca-certificates` (prints "1 added"). Removal: delete the file, then `update-ca-certificates --fresh` ("Fresh updates. Remove symlinks in /etc/ssl/certs directory", then regenerated; the manpage does not describe local-certificate removal explicitly, `--fresh` is the safe form). Needs the `ca-certificates` package; skip distros without `update-ca-certificates` (Fedora-family would need `/etc/pki/ca-trust/source/anchors` and `update-ca-trust`; Alpine uses the same Debian-style directory). Run as `-u root` (no sudo). curl in the distro reads `/etc/ssl/certs/ca-certificates.crt`, which is what the update rewrites; Java and Python `certifi` do not use it.
- ARCHITECTURE.md currently says hlabd runs no `wsl.exe`; CERT-04 changes that (the decision for this phase must record it).
