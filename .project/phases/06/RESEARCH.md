## Corrections and contradictions against CONTEXT (read first)

1. Limit "500 rules": the spec and Hetzner's FAQ say 500 *effective* rules **per firewall**, not per server. An effective rule is one unique IP prefix within one direction; rules for the same prefix are merged, and "an inbound rule that allows port 80 for 8 sources counts as 8". So 50 rules x up to 100 CIDRs per rule can exceed 500 on one firewall. CONTEXT says "Hetzner's limit of 500 rules per server ... not enforced": the deviation text should say per firewall. Whether the API rejects a firewall above 500 effective rules, and with which code, is unclear (generic `403 resource_limit_exceeded` is the likely one, unconfirmed). Source: spec `create_firewall`/`set_firewall_rules`; https://docs.hetzner.com/cloud/firewalls/faq/.
2. `POST /firewalls` error table (spec): `422 server_already_added` (server applied more than once), `422 incompatible_network_type`, `422 firewall_resource_not_found`. CONTEXT lists `404 firewall_resource_not_found` for create. The spec says **422** for create and **404** for `apply_to_resources`/`remove_from_resources`. Use the spec (422 on create). Source: spec lines for `create_firewall`, `apply_firewall_to_resources`, `remove_firewall_from_resources`.
3. `remove_from_resources` request: `remove_from[]` items accept `type` `server` **and** `label_selector` (same `FirewallResource` shape as `apply_to`). So a selector can be removed by selector string. Source: spec `RemoveFromResourcesRequest`.
4. Resolvers 185.12.64.1/2 (CONTEXT Q1 conditional): Hetzner's FAQ says the firewall "will always let through traffic to/from certain Hetzner services ... currently includes DNS resolver traffic and traffic for the Hetzner rescue system". So Hetzner does **not** filter the resolvers by `out` rules; the "otherwise never filtered" branch of Q1 applies. The IPs 185.12.64.1/2 are not named on the page (unclear whether "DNS resolver traffic" means exactly these two). In hlab these addresses are local to the appliance (ARCHITECTURE "Network"; `dnsListen` in `internal/agent/dns.go`), so the traffic takes the INPUT path and a FORWARD-chain firewall never sees it: no extra rule needed. Other DNS servers (e.g. 8.8.8.8) are filtered like any destination. Source: https://docs.hetzner.com/cloud/firewalls/faq/.
5. Metadata 169.254.169.254: Hetzner says metadata requests "don't pass through the firewall; they're answered locally" (the address itself is not on the page). Same as CONTEXT Q1 (never filtered, no deviation to record). In hlab it is also an appliance-local address (INPUT path).

## 1. Hetzner firewall API (frozen spec)

Endpoints: `GET/POST /firewalls`, `GET/PUT/DELETE /firewalls/{id}`, `GET /firewalls/actions`, `GET /firewalls/actions/{id}`, `GET /firewalls/{id}/actions`, `GET /firewalls/{id}/actions/{action_id}`, `POST /firewalls/{id}/actions/{apply_to_resources,remove_from_resources,set_rules}`. All three POST actions return `201` `{actions: [...]}`. `POST /firewalls` returns `{firewall, actions}`. `PUT` takes only `name`, `labels`.

Errors (spec; generic table: 404 `not_found`, 409 `uniqueness_error`/`conflict`, 422 `invalid_input`/`service_error`/`unsupported_error`, 423 `locked`/`protected`, 403 `resource_limit_exceeded`):
- `DELETE /firewalls/{id}`: `422 resource_in_use` ("still applied to a resource"). Applied via selector counts as applied (unclear; the spec says only "a resource").
- `apply_to_resources`: `404 firewall_resource_not_found`, `422 firewall_already_applied`, `422 incompatible_network_type`, `422 private_net_only_server` (server has no public interface).
- `remove_from_resources`: `404 firewall_resource_not_found`, `422 firewall_managed_by_label_selector`. "Already removed" (server not applied): the code `firewall_already_removed` exists in hcloud-go v2.53.0 but is marked deprecated and "no longer used by the API"; what the API does now (404 `firewall_resource_not_found`, or silent success) is unclear. Source: hcloud-go `error.go`. Pick one and record in DECISIONS.md; both pinned clients tolerate `firewall_resource_not_found` on remove (provider `syncApplyTo` and delete treat it as success).
- `POST /firewalls`: see correction 2.
- Not in the spec at all: unknown firewall ID on `GET/PUT/DELETE` and `apply/remove/set_rules` (use generic `404 not_found`); duplicate name (generic `409 uniqueness_error`, "Must be unique per Project"); error code for the 5-firewalls-per-server limit and for >500 effective rules; label selector already applied (the same `firewall_already_applied` is the only documented "already" code; a selector string equal to an existing one is the natural case, unconfirmed); `incompatible_network_type` trigger (unclear; hlab servers always have a public or private-only network, `private_net_only_server` covers the no-public case).
- Protection: no `change_protection` action for firewalls in the spec.

Limits (spec + docs): name 1..128 chars unique per project; rule `description` max 255, nullable; `source_ips`/`destination_ips` at most 100 CIDRs each; 50 rules per firewall (spec says "limited to 50 entries"); 500 effective rules per firewall; 5 firewalls per server, counted over direct and selector-applied firewalls together ("This limit applies to Servers applied via a matching Label Selector as well"); 50 firewalls per project (docs: "across all projects"; the page says projects, per-project scope unclear); 80,000 concurrent connections and 10,000 new connections/s per server (not worth emulating). Limit on `apply_to` entries: not documented (unclear). Sources: spec; https://docs.hetzner.com/cloud/firewalls/overview/.

Rule shape (response requires all of `direction, protocol, destination_ips, source_ips, port`; `port` and `description` nullable). Request requires only `direction`, `protocol`; `source_ips`/`destination_ips` default to empty. Protocol enum: `tcp, udp, icmp, esp, gre`. Direction `in` uses `source_ips`, `out` uses `destination_ips`; the other list is `[]` in responses.
- Port: spec says "Only applicable for tcp and udp"; a range is `lower-upper` ("1024-5000 includes all ports from 1024 up to 5000"). `any` is documented by the provider docs (`port` required for TCP/UDP, "any" or a range such as `80-85`), not by the spec text. Port bounds (1..65535), lower<=upper, whether `0`, leading zeros or `a-a` are rejected, and whether `any` is echoed back as `any` or `1-65535`: unclear. Missing port on tcp/udp: spec says optional in the request, the provider says required; API behaviour unclear (CONTEXT: reject).
- CIDR: must be CIDR notation; "may refer to networks (with empty host bits) or single hosts". Whether host bits set (`10.0.0.5/24`) is rejected or masked: unclear (spec wording suggests rejection; terraform masks before sending, ansible calls `normalize_ip`, so neither client sends it). IPv6 is "transformed to canonical form according to RFC5952" in the response: lower-case, compressed, `/128` kept. A bare address without `/len`: unclear (hcloud CLI rules file parser and hcloud-go use `net.ParseCIDR`, so clients always send a mask). `0.0.0.0/0` and `::/0` are the any-address values.
- ICMP: one `icmp` protocol, no type field. GRE: IPv4 only ("GRE traffic over IPv6 will be dropped"). `esp`/`gre` carry no port.

Actions (spec examples): `set_firewall_rules` resources `[{id: fw, type: firewall}]`; `apply_firewall` and `remove_firewall` resources `[{id: server, type: server}, {id: fw, type: firewall}]`, one action per server (selector: what resources the action names is not documented, unclear; the example shows only a server). `POST /firewalls` with `rules` and `apply_to` returns `actions` containing a `set_firewall_rules` and an `apply_firewall` action (spec example for the 201 shows exactly these two; with several `apply_to` entries presumably one apply action per resource, unconfirmed). Spec: "A Firewall is applied to a resource once the related Action with command `apply_firewall` successfully finished." Selector updates "can take up to a few seconds".
- `applied_to[]` items: `{type: server, server: {id}}` or `{type: label_selector, label_selector: {selector}, applied_to_resources: [{type: server, server: {id}}]}`. Spec lists `applied_to_resources` as an optional property of the item (not in `required`); hcloud CLI prints it only for selectors. Selector firewalls skip servers without a public interface and servers that would exceed 5 firewalls silently (docs: "missing public IPs or exceeded limits can prevent application"), so `applied_to_resources` must exclude them.
- Precedence: "Resources added directly are taking precedence over those added via a Label Selector": a server attached both ways stays attached by the selector when removed directly; `firewall_managed_by_label_selector` only when it is attached solely through a selector.
- Server: `public_net.firewalls: [{id, status}]`, `status` enum `applied | pending` ("Status of the Firewall on the Server"), description "Firewalls applied to the public network interface". `pending` = action not finished yet (also selector additions in flight). The create-server request has `firewalls: [{firewall: <id>}]` ("applied on the Server's public network interface at creation time"). The create-server response actions/next_actions carry the apply actions (spec text not read in full: unclear whether they are `apply_firewall`).

## 2. Hetzner traffic semantics (docs only; nothing run against Hetzner)

- Stateful: yes ("track connections, responses to your server's outbound requests are allowed automatically"); FTP, TFTP, SIP, PPTP secondary traffic is not treated as related. Settings changes "apply only to new connection attempts; existing connections remain active until they end". Source: FAQ.
- Inbound: default DROP once a firewall is applied, even with no rules (spec tag text: "no `in` rule: all inbound dropped"). Outbound: default ACCEPT with no `out` rule; "once you add one or more outbound rules, outbound traffic is denied by default unless a rule permits it". Rule order irrelevant (allow-lists only).
- Several firewalls: "rules are combined and enforced together" (union). Not stated: whether firewall A without `out` rules plus firewall B with `out` rules gives default deny with B's allowances (likely, as "combined") or allow-all; CONTEXT's "outbound allowed until any applied firewall has an out rule" is the natural reading, unconfirmed.
- ICMP: same stateful/default behaviour with exceptions: "ARP, DHCP and some ICMPv6 types like the ones needed for NDP will always be unaffected". ICMP echo needs an `icmp` rule inbound. Related ICMP errors for tracked flows are not described (stateful tracking makes them pass in practice; unclear).
- Private networks: not filtered ("firewalls can't currently secure traffic on private Cloud Networks"). Load balancers: cannot have firewalls yet.
- Floating IP: neither the firewall FAQ nor overview mentions floating IPs; I found no Hetzner source saying whether traffic to a floating IP is filtered by the assigned server's firewalls. Unclear. The Firewalls section applies to "the public network interface" of the server and the floating IP is configured on that interface, so filtering is the plausible behaviour (CONTEXT assumption stays; mark as unverified in deviations.md).
- Label selector gaining a label later: docs say the firewall "updates automatically when server labels change"; spec: up to a few seconds. Status passes through `pending`.

## 3. google/nftables v0.3.0 on the appliance

Existing design: `internal/agent/isolation_linux.go` owns table `inet hlab`, replaced atomically per apply (`AddTable, DelTable, AddTable`); base chains `forward`/`input` at `ChainPriorityFilter`, policy accept; raw-priority `prerouting` sets `ct zone` only for `t<vlan>` interfaces; "no rule uses `ct state`" (DECISIONS 2026-11-19). All public traffic enters and leaves the appliance on the one public interface (promiscuous PVLAN port; default route via 198.19.0.2 on the same adapter), `proxy_arp_pvlan=1`, `send_redirects=0`, `ip_forward=1` (`network_linux.go`).

- Direction must be derived from addresses, not interfaces: `in` = forwarded packet with `ip daddr` a server address (public IPv4 or assigned floating IP), `out` = `ip saddr` a server address. Server-to-server public traffic is matched twice (out of A, in to B), as at Hetzner. Hairpin is no problem for conntrack: conntrack hooks run in prerouting/output, independent of the output interface, so `ct state established,related accept` works for packets forwarded back out the interface they came in (source-derived from netfilter design; no kernel doc says otherwise; not run here, so keep one e2e probe in FW-02/FW-03).
- Conntrack zones: the existing zones apply only to `t<vlan>` ingress, so public flows are in the default zone; no conflict, and FW-04 holds because the firewall chain only matches packets whose iif or oif is the public interface. Conntrack flows of the two tables are the same table (not per nft table). Overlap of private ranges with `198.19.0.0/16`: not possible by the same-zone rule in practice, otherwise a private packet could match a public address; match `iifname`/`oifname` public explicitly.
- A separate table is safe: per the nftables wiki, an `accept` in one base chain "isn't necessarily final" when another base chain exists at the same hook, `drop` is immediate, and "there is no guaranteed evaluation order of base chains with identical priority". So `inet hlab_fw` forward must not rely on order against `inet hlab` (isolation only drops, so it is order independent). Give the firewall chain an explicit priority (e.g. `ChainPriorityFilter + 10`, i.e. `nftables.ChainPriorityRef` arithmetic: `ChainPriority` is `*int32`-like in v0.3.0, check when coding) and leave isolation at filter. Source: https://wiki.nftables.org/wiki-nftables/index.php/Configuring_chains.
- Stateful rule encoding (source-derived from the library, not run): `expr.Ct{Key: expr.CtKeySTATE, Register: 1}`, `expr.Bitwise{SourceRegister: 1, DestRegister: 1, Len: 4, Mask: binaryutil.NativeEndian.PutUint32(expr.CtStateBitESTABLISHED|expr.CtStateBitRELATED), Xor: make([]byte, 4)}`, `expr.Cmp{Op: expr.CmpOpNeq, Register: 1, Data: []byte{0,0,0,0}}`, then `Verdict{Accept}`. Constants in v0.3.0 `expr/ct.go`: `CtStateBitINVALID=1, ESTABLISHED=2, RELATED=4, NEW=8, UNTRACKED=64`. Using any `ct` match loads conntrack for all traffic in the netns (Debian 13 `generic` image has the modules; SPEC says `generic`). `ct state` values per nftables wiki: new, established, related, invalid, untracked. Existing connections survive rule changes by `ct state established` (matches Hetzner "existing connections remain active").
- Port ranges: `expr.Range{Op: expr.CmpOpEq, Register: 1, FromData: binaryutil.BigEndian.PutUint16(lo), ToData: binaryutil.BigEndian.PutUint16(hi)}` after `Payload{DestRegister: 1, Base: PayloadBaseTransportHeader, Offset: 2, Len: 2}` (dport; 0 for sport), preceded by `Meta{L4PROTO}` + `Cmp tcp/udp`. Fields confirmed in v0.3.0 `expr/range.go` (Op, Register, FromData, ToData; big-endian). A single port is a plain `Cmp`; `any` needs no port match (do not use `Range 1-65535`, it would equal any but costs a rule).
- ESP and GRE: `Meta{Key: MetaKeyL4PROTO}` + `Cmp{Data: []byte{unix.IPPROTO_ESP}}` (50) / `unix.IPPROTO_GRE` (47). GRE is IPv4 only at Hetzner; the appliance matches IPv4 only anyway. Conntrack for GRE has a tracker; ESP is tracked by the generic tracker (address pair only), so replies match as established; source-derived, unclear, and not part of the e2e rows (FW-02/FW-03 use tcp).
- ICMP: `L4PROTO == icmp` (1) plus `meta nfproto ipv4`; `ct state related` lets ICMP errors of allowed flows through. Without an `icmp in` rule echo requests from outside are dropped, with `ct state established` replies to the server's own echo pass.
- Prefix match options: per-prefix `Bitwise` mask + `Cmp` (as `addPrivate` does), or interval sets `Set{Interval: true, KeyType: nftables.TypeIPAddr}` with `SetElement{IntervalEnd: true}` entries. At most 100 CIDRs x 50 rules per firewall: sets are cheaper than one rule per prefix; a per-server concatenated set (`ipv4_addr . inet_proto . inet_service`) is also possible but v0.3.0 interval-with-concatenation is the riskiest part; do not use it.
- Appliance-local services (resolvers, metadata, API proxy 198.19.0.1, DNS at 198.19.0.1) use INPUT, so a forward-only firewall never filters them: matches Hetzner (correction 4, 5).
- IPv6: the appliance matches `meta nfproto ipv4`; IPv6 rules are stored but have no effect (CONTEXT). With `inet` family forward chain default policy accept, IPv6 forwarded packets remain unfiltered; that is consistent with no IPv6 in hlab.
- Maintenance: google/nftables v0.3.0 published 2025-02-03, still the latest tag (checked in phase 05); last release ~21 months ago, pseudo-versions on main may exist.

## 4. What the pinned clients read and wait for

Versions found 2026-11-19 (GitHub releases): hcloud CLI v1.70.2 (2026-10-23, latest), terraform-provider-hcloud v1.70.2 (2026-10-26, latest, uses hcloud-go v2.53.0), hetzner.hcloud collection 7.2.0 (2026-10-05, latest).

hcloud-go v2.53.0 action waiting (used by CLI and provider): `Action.WaitFor` polls `GET /actions?id=<ids>&sort=status&sort=id` (chunks of 25; not `GET /actions/{id}`), with backoff; an `error` status returns `ActionError`; if the list returns **fewer** actions than asked it fails with "actions not found" (so action IDs must stay listable after they finish). hcloud-python (used by Ansible) waits by `GET /actions/{id}` until status is not `running` (`ActionFailedException` on `error`, timeout via max retries). The hlab API therefore needs both `GET /actions?id=` (multiple `id` params) and `GET /actions/{id}`; phase 05 already serves both (not re-checked here). `GET /firewalls/actions`, `GET /firewalls/{id}/actions` exist in the spec but no pinned client reads them for firewalls (unclear; hcloud-go has `Firewall` action helpers only via the general client).

- hcloud CLI v1.70.2: `firewall create` (`--name`, `--label`, `--rules-file`, JSON array of rules parsed with `net.ParseCIDR` for each IP, so IPs must carry a mask), `Create` then `WaitForActions(result.Actions)`; `firewall apply-to-resource` / `remove-from-resource`: look up firewall (by name through `GET /firewalls?name=`) and server (`GET /servers`), `ApplyResources`/`RemoveResources`, wait on returned actions; no handling of `firewall_already_applied` (shows the error). `firewall describe` prints rules (`direction, description (if non-nil), protocol, port (if non-nil)`, IPs by direction), `applied_to` (server ID plus name, label selector plus indented `applied_to_resources`), created, labels. Port is printed raw. Output `Firewall <id> created`. Exact file for `apply-to-resource` I could read is `apply_to_resource.go`; the `remove` variant was not read (same pattern assumed).
- Provider `hcloud_firewall` (rules as a set, `port` omitted when empty, `any` passed through; IPs masked with `net.ParseCIDR` before sending): Create -> `Firewall.Create` (name, rules, labels, apply_to) then waits on **every** action in the create response, then Read; Update -> `Update` (name/labels, no wait), `SetRules` + wait, `apply_to` diff via `RemoveResources` first (tolerates `firewall_resource_not_found`) then `ApplyResources`, each waited; Delete -> `RemoveResources` for all `applied_to` (waits; tolerates not found) then `Firewall.Delete` inside a retry (about 2x default retries): retried on `resource_in_use` and `conflict`, `not_found` = success, other errors (including `locked`) abort. No wait after delete. Read: `GET /firewalls/{id}` reads `rules` (direction, protocol, port if non-nil, description if non-nil, IPs), `applied_to` (type server/label_selector; anything else dropped), `labels`, `name`. Consequences: `DELETE` may return `422 resource_in_use` right after a remove action finishes only while `applied_to` still lists the server, so the record must change when the remove action succeeds (or the retry covers it); a response that omits `port` for icmp is fine (read as nil) but a response with `port: "any"` must echo what was sent, else set diffs appear.
- Provider `hcloud_firewall_attachment` (`firewall_id`, `server_ids`, `label_selectors`): Create -> `ApplyResources` (servers and selectors), treats `firewall_already_applied` as success (no wait), else waits on returned actions, then Read; Read -> `GET /firewalls/{id}`, `server_ids` from `applied_to` type server, `label_selectors` from type label_selector, any other `applied_to` type is an error; Delete -> `RemoveResources` and wait, no special handling of not found. Update diffs desired vs live `applied_to`. Does not read `applied_to_resources`.
- Provider `hcloud_server.firewall_ids`: Create sends `firewalls: [{firewall: id}]` and waits on `action` and each `next_actions`; Update (changed `firewall_ids`) works from `server.public_net.firewalls` of a fresh `GET`: `RemoveResources` for dropped IDs (waits), `ApplyResources` for added (waits); Read maps `public_net.firewalls[].id` only, **status is never read or filtered** (pending is shown as attached). Note: it removes firewalls that are attached through a selector too, since they appear in `public_net.firewalls`; hence the server record must list them or the provider will diff `firewall_ids` (users usually set `ignore_remote_firewall_ids`). Also the update path calls remove for a selector-only firewall and would get `422 firewall_managed_by_label_selector`.
- Ansible `hetzner.hcloud.firewall` 7.2.0: create `firewalls.create(name, labels, rules)`; update by `update(name)`, `update(labels)`, `set_rules` when the normalised rule list differs (order-sensitive comparison of `direction, protocol, port, source_ips, destination_ips, description`; IPs run through `normalize_ip`, so the API must return canonical CIDRs in the order given, else the module reports changes each run); **does not wait for create/set_rules actions**; re-fetches the firewall after create/update; reads `id, name, labels, rules, applied_to` (type, server id, selector, `applied_to_resources` when present). Delete: with `force` it removes all `applied_to` resources and waits per action, then deletes; the delete retries up to 10 times sleeping 0.5 x n seconds when the error message contains the text "is still in use" (so the `resource_in_use` message must contain "is still in use"). Missing port: not sent for icmp/esp/gre (argspec requires it only for tcp/udp).
- Ansible `hetzner.hcloud.firewall_resource`: `servers` (name or ID), `label_selectors`, `state`; compares live `applied_to` (server names via `server.name`, selector strings) and calls `apply_to_resources`/`remove_from_resources` only for differences (so no `firewall_already_applied` in normal use), waits for each returned action, then reloads; ignores `applied_to_resources`.
- Ordering: no pinned client relies on the order of rules or of `applied_to`, except Ansible's rule list comparison (keep rules in the order given by the user, and the IPs within a rule in the given order, with IPv6 canonicalised).
