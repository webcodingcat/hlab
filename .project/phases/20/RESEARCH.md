### 1.3 Does 1024 MB of RAM suffice with all daemons running?

UNCONFIRMED by measurement; the numbers below are estimates. No source gives per-process memory for these versions (Samba list: RSS figures from 120 MB per process down to 0.4 MB unshared, "ps and top are not good tools"; no Apache number found).
- Fixed: kernel, systemd, journald, cloud-init, one sshd, hlab storage agent, btrfs metadata and qgroup state: about 200-300 MB (kernel page cache is reclaimable).
- smbd: one parent plus one process per client connection; expect roughly 5-15 MB unshared each.
- Apache with mpm-itk is prefork (README.Debian: "no longer a true MPM, a module that hooks into prefork"): one process per connection, about 5-10 MB each. Debian's `mpm_prefork.conf` is `StartServers 5, MinSpareServers 5, MaxSpareServers 10, MaxRequestWorkers 150, MaxConnectionsPerChild 0` (read from 2.4.71-1~deb13u1): 150 workers could reach 1 GB alone. Set e.g. `StartServers 2, MinSpareServers 2, MaxSpareServers 4, MaxRequestWorkers 20` (and `MaxClientsVHost` per box if wanted).
- vsftpd: 2 small processes per session (about 1-2 MB). sshd about 5 MB per session.
- Conclusion (INFERRED): 1024 MB is enough for idle and for the handful of concurrent test clients of the e2e suite if Apache is limited as above; it is not enough for Apache's defaults under load. Measure `free -m` / `smem` once in the first e2e run after all daemons run with clients connected and record it; raising the VM to 1536/2048 MB is the fallback.

## 2. Samba

Version in trixie: 4.22.11+dfsg-0+deb13u1 (E16, E17 ran 4.22.11).

- Reload without dropping sessions (CONFIRMED in part): `smbcontrol smbd reload-config` = "Force daemon to reload smb.conf configuration file" (smbcontrol(1)). Samba docs and list threads: already established connections keep their old configuration; changes show for new connections (list answer of 2014, not official text; smb.conf(5) says active connections are not changed). Whether changed `include` files are re-read: `include` "takes the standard substitutions, except %u, %P and %S", "included literally as though typed in place" (smb.conf(5), CONFIRMED), so `include = /etc/samba/ip-%i.conf` (as E16) is valid; a 2014 thread disputes whether `reload-config` re-reads included files, one user reports `smbcontrol all reload-config` does (UNCONFIRMED: probe by changing `ip-<ip>.conf` and opening a new connection). Samba also re-reads changed config files by itself about once a minute (INFERRED from source). Write the include file atomically (temp + rename), run `testparm -s` first, then `smbcontrol smbd reload-config`; no other box's session is dropped.
- `hosts allow` per share: it is a share-level parameter (S): "if specified in the [global] section then it will apply to all services", a share's own list overrides the global one; "access still requires suitable user-level passwords"; localhost is always allowed unless denied; allow wins over deny when they conflict (smb.conf(5), CONFIRMED). Put it in the share inside the per-IP include: `hosts allow = <PublicRange> EXCEPT <transit /30>` for a share without reachable_externally. The `EXCEPT` operator and CIDR notation of `hosts allow` were not in the excerpt fetched (known from the man page; UNCONFIRMED here, probe with `testparm` and a connect from the transit net). A refusal is logged as "Denied connection from" and the client sees `NT_STATUS_ACCESS_DENIED` at tree connect (INFERRED). A leading space in the parameter name makes testparm report "Unknown parameter" and the line is ignored: always run `testparm`.
- A changed `hosts allow` does not kick connected sessions. smbcontrol also has `close-denied-share <share>` ("like close-share, but does not disconnect users who are still allowed") and `close-share <share>` ("close the client connections to the named share"). The share name `backup` is the same for every box, so `close-share backup` hits ALL boxes; `kill-client-ip <ip>` ("close the client connections from a given IP address") hits all boxes of that client. Neither is per box.
- Ending one box's SMB sessions (INFERRED, UNCONFIRMED by test): smbd forks one process per TCP connection. Find them by the local (box) address: `ss -tnpH state established '( sport = :445 )' src <boxip>` shows `users:(("smbd",pid=N,...))`; then `kill -TERM N` (or `smbcontrol N close-share backup`, destination "If a single process ID is given, the message is sent to only that process"), or `ss -K` on the same filter. `smbstatus` shows share, user and client machine but not the server address (UNCONFIRMED), so it cannot select by box; a subaccount of the same box has its own share name and can be selected by `smbstatus -S`. SMB3 multichannel/durable handles: after killing, a client may try to reconnect a durable handle by dev/inode; consider `durable handles = no` (valid parameter, effect on rollback not tested).
- Refusing an account with samba_enabled off: with the account absent from tdbsam (`pdbedit -x -u <name>`), session setup fails with `NT_STATUS_LOGON_FAILURE`; with the account present but disabled (`pdbedit -c "[D]"`, `smbpasswd -d`) `NT_STATUS_ACCOUNT_DISABLED` (INFERRED from Samba behaviour, not fetched). The share missing from the IP's include gives `NT_STATUS_BAD_NETWORK_NAME` at tree connect. For a whole box with samba_enabled off the cleanest match to Hetzner (port closed) is an nftables rule in the storage VM that rejects TCP 445 to that box IP (needs `nft`, see 1.1); alternatively an empty include so that the box has no share. E17 observed: credentials of one box do not work at another box's IP over SMB.
- Hetzner side (docs.hetzner.com access-overview, CONFIRMED): the SMB share name of a subaccount is its user name; port 445 needs the setting "Samba"; FTP and SFTP (22) are always on.
- Pitfalls: disable NetBIOS (`disable netbios = yes`, `smb ports = 445`, nmbd off); `samba` Recommends python3-samba is not needed; the Samba package creates the `sambashare` group and `/var/lib/samba/usershares`; `pdbedit --set-nt-hash` per E19.

## 3. Apache 2.4.71 with mpm-itk

- Module mechanics (CONFIRMED, Debian sources of mpm-itk 2.4.7-04-2): `mpm_itk.load` is `# Depends: mpm_prefork` + `LoadModule mpm_itk_module /usr/lib/apache2/modules/mpm_itk.so`; `mpm_prefork.load` has `# Conflicts: mpm_event mpm_worker`; the package postinst only switches MPM on an upgrade from before 2.4.7-02-1.1 (as read), so on a fresh install do it yourself: `a2dismod -f mpm_event; a2enmod mpm_prefork mpm_itk ssl dav dav_fs auth_basic authn_file authz_user authz_host headers` (all module files exist in 2.4.71-1~deb13u1 mods-available; the exact a2enmod behaviour with the conflict is UNCONFIRMED, E17 worked). HTTP/2 does not work with prefork.
- `AssignUserID <user> <group>` inside every `<VirtualHost>`. The mpm-itk README (2.2.3 version read) says the process runs as root until the request is parsed and the vhost known, and that a vhost without AssignUserID gets no uid change: give EVERY vhost including a catch-all an `AssignUserID` (a catch-all with `nobody nogroup` or the box user). If a client reuses a connection for a request of a different vhost, mpm-itk closes the connection (README), expected for browsers fetching cross-vhost resources only. `MaxClientsVHost <n>` limits one vhost's workers (README). The module is prefork-based: one process per connection.
- Several SNI vhosts per box IP: `Listen <boxip>:443` per box (not the wildcard `Listen 443` of Debian's ports.conf) and `<VirtualHost <boxip>:443>` blocks, one per account: `ServerName u100000-sub1.storagebox.hetzner.internal`, own `SSLCertificateFile/KeyFile`, `AssignUserID u100000 u100000`, `DocumentRoot` (or `Dav On` in `<Location />` with `DavLockDB`). Name matching first narrows by IP:port, then by ServerName/ServerAlias in file order (Apache vhost docs, CONFIRMED); the SSL FAQ says a client without SNI gets the first vhost's certificate. Put the box's main-account vhost first in each IP group so it is the default for that IP; vhosts of other boxes are never candidates because the IP differs.
- Unknown Host or SNI on a box IP (CONFIRMED docs, INFERRED combination): no match -> "the first listed virtual host" for that IP:port (the box's main vhost, after authentication). In 2.4.66+ `SSLVHostSNIPolicy` defaults to `secure`: when the vhost found by Host differs from the vhost found by SNI and their certificates/ciphers differ, the request gets `421 Misdirected Request`; with equal certificates it passes. `SSLStrictSNIVHostCheck on` refuses non-SNI clients altogether (handshake-level; status code not specified). To answer unknown names with an error instead of the main vhost, list a catch-all vhost first per IP (own certificate, `AssignUserID nobody nogroup`, `Require all denied`); a client with an unknown SNI then sees its certificate (name mismatch warning) and 403.
- Read-only accounts limited to GET, HEAD, OPTIONS, PROPFIND: `Require method GET HEAD OPTIONS PROPFIND` works ("GET and HEAD are treated as equivalent"; TRACE is not available to the provider) and PROPFIND is registered by mod_dav. mod_dav's own example uses `<RequireAny>`. To require BOTH login and a method inside a `<Location />` with `AuthType Basic`:
  `<RequireAll> Require valid-user / Require method GET OPTIONS PROPFIND </RequireAll>`. The authz doc does not show this combination; by its result table a denied `method` fails the RequireAll (INFERRED, probe: a PUT by the read-only account must give 403, an unauthenticated GET 401). `AuthMerging` is Off by default, so section-local `Require` replaces inherited ones. `<LimitExcept GET HEAD OPTIONS PROPFIND> Require all denied </LimitExcept>` is the older alternative (not fetched). Also deny `LOCK/UNLOCK/PROPPATCH/COPY/MOVE/MKCOL/PUT/DELETE/POST` (all excluded by the list).
- Source network for subaccounts without reachable_externally: `<RequireAll> Require valid-user / Require ip <PublicRange> / Require not ip <transit/30> </RequireAll>` (mod_authz_host; not fetched, standard).
- LOCK pitfall (INFERRED from mod_dav docs): the directory of `DavLockDB` must be writable by "the User and Group under which Apache is running"; under itk that is the vhost user, but Debian's `dav_fs.conf` puts the lock DB in a directory owned by www-data. Windows WebDAV and many clients LOCK before writing. Use `DavLockDB` per vhost (context server/virtual host) in a directory owned by the box user, e.g. `/var/lib/hlab/davlock/<user>/lock`. E17 tested only PUT, MKCOL, PROPFIND. `DavDepthInfinity` stays off; set `LimitXMLRequestBody`.
- Graceful reload (CONFIRMED, httpd stopping docs; Debian unit has `ExecReload=/usr/sbin/apachectl graceful`, `PrivateTmp=true`, `KillMode=mixed`): children finish their current request then exit, new connections are queued by the OS, not lost; a syntax check runs first and a failing config refuses the restart (old server keeps running, implied); semantic errors are not caught by it (run `apachectl configtest` / `httpd -t` first). Listen changes on graceful are not described in the page (UNCONFIRMED): after adding a box IP verify with `ss -ltn`; a full `restart` drops sessions. Plan: the storage agent adds the IP to the interface before the reload, and tests with a probe.
- Ending one box's Apache sessions: itk children run as the box uid after the request is parsed, so `pkill -KILL -U <uid>` hits them (the shared uid also hits other protocols of the same box, intended at rollback), plus `ss -K`/kill by `src <boxip>:443`.

## 4. vsftpd 3.0.5 (Debian 3.0.5-0.2)

- One certificate for all addresses (CONFIRMED options): `ssl_enable=YES`, `rsa_cert_file`, `rsa_private_key_file`, `ssl_tlsv1_2/ssl_tlsv1_3=YES`, `ssl_sslv2/3=NO`, `force_local_logins_ssl`/`force_local_data_ssl` to enforce TLS (leave NO if plain FTP is also required: the e2e needs FTP and FTPS, E17), `require_ssl_reuse` default YES ("may break many FTP clients", disable it). `ssl_ciphers` default `DES-CBC3-SHA` per the man page text read: set a modern value. The certificate must carry the SANs of all boxes/accounts or clients verify against the box name only (a SAN or wildcard certificate of the hlab CA; the clients skip verification or trust the CA per decisions/storage-box.md). `implicit_ssl` is port 990, not needed.
- `listen_address` takes ONE address and standalone mode binds once (standalone.c: a single socket; CONFIRMED in source). So do not set it: `listen=YES` binds all addresses of port 21. Passive replies: `pasv_address` "override[s] the IP address that vsftpd will advertise in response to the PASV command" and its default is none, so the advertised address is the local address of the control connection (man page: default none; E17 saw passive FTP/FTPS working through the routed hop). Do not set `pasv_address`; set `pasv_min_port=50000`, `pasv_max_port=50099` (E17). `pasv_promiscuous` stays NO.
- Active mode does not work through the hop (E17); EPSV is covered by the same range.
- `pam_access` by source network: vsftpd calls `pam_set_item(PAM_RHOST, <remote host string>)` and `pam_acct_mgmt` in `vsf_sysdep_check_auth` (sysdeputil.c 3.0.5-0.2, CONFIRMED); Debian's `/etc/pam.d/vsftpd` is `auth required pam_listfile.so item=user sense=deny file=/etc/ftpusers onerr=succeed`, `@include common-account`, `@include common-session`, `@include common-auth`, `auth required pam_shells.so` (the user's shell must be listed in `/etc/shells`: E17 used `/bin/sh`). Add before the account include: `account required pam_access.so accessfile=/etc/security/vsftpd-access.conf` (`pam_access.so` is in libpam-modules, present). access.conf format (CONFIRMED, access.conf(5)): `permission:users:origins`, first matching line decides, `EXCEPT` operator, `ALL`, IPv4 as `192.168.201.0/24` or with a mask, so: `-:u100000-sub1:ALL EXCEPT 198.19.0.0/16`? is wrong direction; write the refusal as `-:u100000-sub1:<transit /30>` first, then `+:ALL:ALL`, or `+:u100000-sub1:<PublicRange> EXCEPT <transit /30>` then `-:u100000-sub1:ALL`. The file is read at every login, so no reload. Caveat: a Red Hat KB (subscriber page, summary only) reports virtual users failing with pam_access enabled: here the users are real local users with the shared box UID (E17), UNCONFIRMED whether affected; probe. Login-time denial returns `530 Login incorrect`.
- Account differences without restart: `user_config_dir=/etc/vsftpd/users` (per-user override, read at login; "not all settings are effective on a per-user basis"), e.g. `write_enable=NO` for read-only subaccounts and `local_root` (E17 used chroot `/srv/chroot/$USER/home`). Passwords come from PAM/shadow, so a password change is live.
- Reload (CONFIRMED in source): Debian's unit has `ExecReload=/bin/kill -HUP $MAINPID`; standalone.c installs `handle_sighup`, which resets tunables to defaults and re-reads the config file in the listener. Existing sessions are separate forked processes that keep their config, so they are not killed; the listening socket is not re-bound (a changed `listen*` option needs a restart). Because the config has no per-box content (wildcard listen, one certificate), a reload is rarely needed; only a changed certificate or global option. (Note: there is no check of the returned value: an invalid config is silently ignored on HUP.)
- Ending one box's FTP sessions: each session is a forked privileged parent plus an unprivileged child running as the box uid. `ss -tnpH src <boxip>:21` (control) and `src <boxip>:50000-50099` (data; filter `sport >= :50000 and sport <= :50099`) list the sockets with their pids; `ss -K` destroys sockets (needs `CONFIG_INET_DIAG_DESTROY`; a Red Hat bug says Debian enables it; verify `grep CONFIG_INET_DIAG_DESTROY /boot/config-$(uname -r)`; without it `ss -K` does nothing), or `pkill -KILL -U <box uid>` for the unprivileged children (the privileged parents exit with them). Debian does not enable `session_support`; no utmp entries to clean.
- `tcp_wrappers` is an alternative but needs `/etc/hosts.allow`; pam_access is simpler.
- Debian's postinst/unit: `vsftpd.service` is `Type=simple`, `ExecStart=/usr/sbin/vsftpd /etc/vsftpd.conf`; the stock `/etc/vsftpd.conf` has `listen_ipv6=YES`/`listen=NO`: set `listen=YES` and `listen_ipv6=NO` (the two cannot be both set: the daemon exits with "run two copies of vsftpd for IPv4 and IPv6").

## 5. Hetzner Storage Box behaviour (not settled by the frozen API description)

Sources: docs.hetzner.cloud/hetzner.spec.json (read in chunks; same file as `api/hetzner-openapi.lock`), docs.hetzner.com/storage/storage-box/{snapshots,access/access-overview,getting-started/creating-snapshots}, robot.hetzner.com/doc/webservice (legacy API), Ansible collection docs.

- Error when `snapshot_limit` is reached (manual create): UNCONFIRMED for the new API. The spec lists only generic error codes (`unauthorized`, `timeout` as examples; `action_failed` for actions) and no snapshot-specific text; hcloud-go has no storage-box error constants (only the generic `resource_limit_exceeded`, `conflict`, `invalid_input`...). The legacy Robot API answers `409 SNAPSHOT_LIMIT_EXCEEDED` ("Snapshot limit exceeded") for `POST /storagebox/{id}/snapshot` (CONFIRMED, legacy). Suggestion: `409` with code `conflict`, or the Cloud API's `resource_limit_exceeded` (status unverified, 403 in the Cloud API as far as known); pick one and state it in `docs/deviations.md`. Clients do not branch on it. Docs for the console say: the limit is 10/20/30/40 manual snapshots (type's `snapshot_limit`, "Maximum number of allowed manual snapshots") and 10/20/30/40 automatic slots (`automatic_snapshot_limit`, "Maximum number of snapshots created automatically by a snapshot plan"); only automatic snapshots rotate ("oldest snapshot will automatically be deleted as soon as a new snapshot is created"), manual ones "are never deleted automatically".
- Automatic snapshot names (CONFIRMED from the spec examples): manual `2025-02-12T11-35-19` (timestamp, `is_automatic false`), automatic `snapshot-daily--2025-02-12T22-00-02` (`is_automatic true`). Only the `snapshot-daily--` prefix example exists; whether weekly or monthly plans use other prefixes is UNCONFIRMED (no source). The list endpoint supports `is_automatic` filtering and "Both snapshots created manually and by the snapshot plan are returned". Names are set by the API and not changeable (Ansible module doc); the legacy API shows plain timestamps.
- `day_of_week` plus `day_of_month` combined: UNCONFIRMED. The spec only states each field's meaning (day_of_week 1 Monday to 7 Sunday, null every day; day_of_month 1-31, null every day) and "The time-related options are cron like"; the table shows each alone. The Ansible doc says null means every day "unless there are other restrictions", which reads as AND. Plain cron would OR them when both are restricted. Recommendation: AND (a day must satisfy both), document it in deviations.md; SBOX-17 is a unit test, so it can pin either choice.
- Automatic snapshots and an action: UNCONFIRMED. Manual create and delete return an action (`create_snapshot`, `delete_snapshot`), `enable_snapshot_plan` returns an action (`enable_snapshot_plan`), `rollback_snapshot` returns an action listing `storage_box` and `storage_box_snapshot`. No text says the plan's automatic runs create an action; hlab can skip creating one.
- Rollback and newer automatic snapshots: CONFIRMED (spec): `rollback_snapshot` "will remove all newer Storage Box Snapshot and irrevocably delete all data that was since written"; docs.hetzner.com: "newer files and snapshots are deleted" (example: restoring Snapshot 1 deletes Snapshot 2). Not limited to manual ones: all newer snapshots, automatic included (the text does not distinguish; INFERRED).
- `.zfs` for subaccounts: UNCONFIRMED. Docs: snapshots appear in `/.zfs/snapshot` or `/home/.zfs/snapshot` over SSH on port 23 (the box root), read-only, switchable with "Display snapshot directory" (= API `zfs_enabled`, "Whether the ZFS snapshot folder is visible"); hidden snapshots still use space. A subaccount sees only its own subdirectory, so the box-root `.zfs` is outside of it (INFERRED); one forum quote says a subaccount "will never have access to the snapshots" (anecdotal). Recommendation: the main account sees `.zfs/snapshot` at its root; subaccounts do not (E17 layout already keeps snapshots outside account chroots).
- FTP and access settings: CONFIRMED (access-overview): FTP/FTPS port 21 and SFTP/SCP port 22 are "always active and cannot be disabled" and tied to no setting; port 23 needs "SSH", 445 "Samba", 443 "WebDAV" (free, set in Console). "External Reachability" applies to access from outside the Hetzner network for the box. The page names no separate settings for subaccounts' protocols (the API does have per-subaccount `access_settings`, already modelled).

## 6. btrfs rollback while Samba, Apache and vsftpd hold files open

Facts (CONFIRMED, btrfs docs): subvolumes can be renamed/moved; `delete` removes the directory instantly and the data "later in the background" (the documentation does not say what happens for a mounted subvolume or open files); `subvolume sync` waits until deleted subvolumes are gone (before btrfs-progs 7.4 the cleaner wakes about every 30 s, so Debian 13's 6.14 may wait up to ~30 s); `snapshot -r` read-only, `-i` qgroup; snapshots are not recursive; a subvolume mount "works like a bind mount". Not documented (UNCONFIRMED, probe): whether `btrfs subvolume delete home.old` returns EBUSY while a bind mount of it exists or files in it are open.

E17 showed: after `mv home home.old` the bind mounts still point to the renamed directory, so users see the old data until the mounts are redone. Layout assumed (E17/ARCHITECTURE): all services reach the data through the chroot bind mounts `/srv/chroot/<user>/home` of the box and each subaccount, and Samba, Apache and vsftpd use those paths or the box's subvolume path; if any service uses another path (for example a DocumentRoot straight under the subvolume), that path is also unusable during the swap and the plan must keep every path in one list.

Proposed order for one box (all steps under the box's lock; the agent job `rollback`):
1. Fence: add an nftables reject for TCP 21, 22, 23, 443, 445 and 50000-50099 to the box IP (new connections get a refusal; the appliance chain cannot be used: it only drops/returns). Stop issuing agent changes for this box. (If `nft` is not installed, use iptables from the image, or skip the fence and accept a brief race.)
2. End sessions per protocol, then verify: for every protocol, `ss -K state established src <boxip>` or kill the pids that `ss -tnp src <boxip>:{21,22,23,443,445}` show (smbd children, sshd session children, vsftpd children, apache children); `pkill -KILL -U <box uid>` (shared uid of box and subaccounts) for sshd/vsftpd/apache children; smbd children run as root with a per-operation impersonation, so select them by socket, not by uid. Wait with a deadline until `fuser -vm /srv/chroot/<user>/home` (psmisc, present) and the same for each subaccount mount and `.zfs/snapshot` are empty.
3. Unmount the box's mounts: `.zfs/snapshot` read-only bind, the subaccounts' `home` binds, the box's `home` bind (innermost first). If `umount` gives EBUSY after step 2, `fuser -km <mnt>` once, retry, last resort `umount -l` (lazy: the name leaves the tree at once, the remaining holders keep the old data until they close; acceptable only after step 2).
4. Swap (E18 order): `mv home home.old`; `btrfs subvolume snapshot -i 1/<n> <snapshots>/<user>/<name> home` (writable snapshot of the chosen snapshot, qgroup `1/<n>`); delete the newer snapshots (`btrfs subvolume delete`, read-only subvolumes outside the mounts); `btrfs subvolume delete home.old`; `btrfs subvolume sync` (bounded wait, see above); `btrfs qgroup clear-stale`; check `qgroup show` for "inconsistent" and `quota rescan -w` (E18 rules). Recreate each subaccount's `home_directory` inside the new `home` if the snapshot lacks it (`mkdir -p` with the box uid), otherwise the bind in step 5 fails; Hetzner behaviour for that case is unknown.
5. Rebind: `mount --bind home /srv/chroot/<user>/home`, each subaccount's subdirectory bind, then `.zfs/snapshot` as bind plus `mount -o remount,bind,ro` (needs the second call; only when zfs_enabled), and set propagation private if the tree is shared.
6. Unfence (remove the nft rule). New connections see the restored data. Apache needs no reload (paths unchanged, itk children are new); `DavLockDB` entries of the box refer to old paths: delete the box's lock DB at step 2 (INFERRED). Samba's `smbd` need no reload either (no config change); stale durable-handle reconnects are the only SMB oddity (see 2).
Pitfalls: a lingering process with a file or cwd in `home.old` delays the data cleanup and makes `subvolume sync` wait; `apache2.service` runs with `PrivateTmp=true`, so it has its own mount namespace (systemd makes it `slave`, so host unmounts and mounts propagate: INFERRED; do not add `ProtectSystem=`/`ReadWritePaths` without testing this); never run `umount -l` before step 2; do not do the swap with the fence off, or a client may write into `home.old` between `mv` and `delete` and lose data silently.
