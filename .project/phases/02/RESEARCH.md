# Phase 02 research

Researched 2026-11-18. Spec = frozen OpenAPI description (`%LOCALAPPDATA%\hlab\openapi\cloud.spec.json`; `info.description` = prose sections, line numbers refer to that file). Error statuses are in CONTEXT.md and skipped.

## 1. OpenTofu provider hetznercloud/hcloud 1.70.2

- Version: 1.70.2 is the pinned one; release 2026-10-26 (security fix, TSIG key sensitive; nothing for ssh_key or placement_group). Newer releases not checked. Source: https://api.github.com/repos/hetznercloud/terraform-provider-hcloud/releases/tags/v1.70.2
- Endpoint: provider argument `endpoint` (optional, default `https://api.hetzner.cloud/v1`), env `HCLOUD_ENDPOINT` is the default of that argument (hcloud/provider.go, v1.70.2). Applied with `hcloud.WithEndpoint`. Docs page itself names only `HCLOUD_TOKEN`; the env var comes from the code. There is also `endpoint_hetzner` / `HETZNER_ENDPOINT` (default `https://api.hetzner.com/v1`, storage-box and DNS style APIs); not needed here. Sources: https://raw.githubusercontent.com/hetznercloud/terraform-provider-hcloud/v1.70.2/hcloud/provider.go and https://raw.githubusercontent.com/hetznercloud/terraform-provider-hcloud/v1.70.2/docs/index.md
- Surprise: the provider rejects a token that is not exactly 64 characters ("entered token is invalid (must be exactly 64 characters long)"). hlab project tokens must be 64 characters or the harness fails at provider configure. Source: provider.go above.
- Polling: `poll_interval` default `500ms`, `poll_function` `exponential` (default) or `constant`. Action polling is `GET /actions/{id}` via hcloud-go. Same source.
- Plain `http://` endpoint: no scheme check in provider code seen; hcloud-go concatenates endpoint + path. Not proven end to end against a non-TLS endpoint here (CLI/Python are proven in phase 01 per the repo's api-transport decision for hcloud CLI only).
- `hcloud_ssh_key` (internal/sshkey/resource.go):
  - create: `POST /ssh_keys` {name, public_key, labels}; no action polling (spec: 201, no action).
  - read: `GET /ssh_keys/{id}`; hcloud-go turns 404 into nil, then the resource is removed from state (no error).
  - update: one `PUT /ssh_keys/{id}` carrying only changed `name` and/or `labels` (labels sent only when changed). `public_key` has RequiresReplace, so a key change is delete + create.
  - delete: `DELETE /ssh_keys/{id}`; 404 is treated as success. Spec: 204.
  - import passes the ID through, then read.
- `hcloud_placement_group` (internal/placementgroup/resource.go):
  - create: `POST /placement_groups` {name, type, labels?}. Spec: 201 with `placement_group` and a nullable `action` (`ActionNullable`, line 40125). Provider calls `Action.WaitFor` on the returned action, so if hlab returns an action it must be pollable via `GET /actions/{id}` (or return `null`).
  - read: `GET /placement_groups/{id}`; 404 -> removed from state.
  - update: `GET /placement_groups/{id}` first, then SEPARATE PUTs: one `PUT /placement_groups/{id}` {name} if the name changed, one {labels} if the labels changed (hcloud-go sets `name` only when non-empty, `labels` only when non-nil). No action polling. Then read.
  - delete: `DELETE /placement_groups/{id}` with no prior GET, no action; spec 204. A 404 here is NOT swallowed by the provider (unlike ssh_key).
  - So PUT must accept a body with only `name` or only `labels` and leave the other untouched (CONTEXT says "PUT replaces the whole label set"; that applies to `labels` when present; an absent `labels` must not wipe them).
- No list/query parameters are sent for these resources in normal create/read/update/delete. Data sources (not used here) would send `name`, `label_selector`.
- hcloud-go for the provider is not pinned in my findings; CLI 1.70.2 uses hcloud-go v2.53.0 (released 2026-10-22).

## 2. Ansible hetzner.hcloud 7.2.0 + hcloud-python 2.27.0

- Versions: collection 7.2.0 released 2026-10-05 (tag `7.2.0`, no `v`); hcloud-python 2.27.0 released 2026-10-05 (PyPI latest 2.27.0, Python >= 3.10). The collection does not pin an hcloud version in requirements.txt (only python-dateutil, requests); 7.2.0 vs 2.27.0 compatibility is not stated anywhere I found, but they are the same-day pair. Sources: https://api.github.com/repos/ansible-collections/hetzner.hcloud/releases/tags/7.2.0, https://api.github.com/repos/hetznercloud/hcloud-python/releases/tags/v2.27.0, https://pypi.org/pypi/hcloud/json
- Endpoint: option `api_endpoint` (alias `endpoint`), env `HCLOUD_ENDPOINT`, default `https://api.hetzner.cloud/v1`; `api_token` env `HCLOUD_TOKEN`. Source: https://raw.githubusercontent.com/ansible-collections/hetzner.hcloud/7.2.0/plugins/doc_fragments/hcloud.py
- `server_info` options: `id`, `name`, `label_selector`. Exactly one lookup, in this precedence (plugins/modules/server_info.py): `id` -> `GET /servers/{id}`; `name` -> `GET /servers?name=<name>` (get_by_name = `_get_first_by(get_list, name=...)`, which sends no page/per_page); `label_selector` -> `GET /servers?label_selector=...&per_page=50&page=N`; none -> `GET /servers?per_page=50&page=N`. The module reads attributes from the returned server objects (image, server_type, location, placement_group, networks, protection) and makes no further calls in the code seen; whether any attribute access triggers lazy requests is not confirmed (BoundServer constructor makes none). Sources: server_info.py (main and 7.2.0), https://raw.githubusercontent.com/hetznercloud/hcloud-python/v2.27.0/hcloud/servers/client.py
- hcloud-python paging: `_iter_pages` sends `per_page=50` and starts at page 1, continues only while `meta.pagination.next_page` is set (last_page unused). So `next_page` must be null/absent on the last page. Source: https://raw.githubusercontent.com/hetznercloud/hcloud-python/v2.27.0/hcloud/core/client.py
- hcloud-python HTTP: `Authorization: Bearer`, `Accept: application/json`, User-Agent `hcloud-python/<version>`; endpoint string concatenated with the path, no scheme check; retries (up to 5) on 502/504 and codes `rate_limit_exceeded`, `conflict`, `bad_gateway`, `timeout`. Source: hcloud/_client.py v2.27.0.
- Pitfall: the module result for an unknown `name` is an empty list without error (get_by_name returns None).

## 3. hcloud CLI v1.70.2: `server-type list`

- Released 2026-10-23 (only a Go toolchain bump). go.mod: hcloud-go v2.53.0. Sources: https://api.github.com/repos/hetznercloud/cli/releases/tags/v1.70.2, https://raw.githubusercontent.com/hetznercloud/cli/v1.70.2/go.mod
- Request: `ServerType().AllWithOpts` -> `GET /server_types?per_page=50&page=1` (hcloud-go sets `per_page=50` when 0; `page` added when > 0; `name` only if given via `--name`-like filter; `sort` only if the opts hold sort entries, and the CLI declares no sort option, so none sent). Not checked against hlab's catalog.

## 4. WSL from a LocalSystem service

- WSL is per Windows user: WslService runs as SYSTEM but keeps a separate instance per user, and distributions registered by a user are invisible to other accounts (SYSTEM, built-in Administrator). From a LocalSystem process `wsl.exe -l` normally shows no distributions. Not confirmed: whether `wsl.exe` from SYSTEM starts a VM at all, and which commands (e.g. `--status`, `--version`) are VM-free. No official Microsoft page documents running wsl.exe as SYSTEM. Sources: https://learn.microsoft.com/windows/wsl/troubleshooting (built-in Administrator remark), https://github.com/microsoft/WSL/issues/11894 (service runs as SYSTEM), community report (PSADT forum) that SYSTEM does not see user distros.
- `wslinfo` is a Linux binary (`/usr/bin/wslinfo`) inside a distro, so using it means starting the user's distro/VM through `wsl.exe -d` in that user's context. It cannot run as pure host detection. Reading `.wslconfig` (what CONTEXT decides) avoids this. `wslinfo --networking-mode` prints one of: `nat`, `bridged`, `mirrored`, `consomme` (for virtioproxy/consomme), `none` (any other mode value), `wsl1` (WSL1 distro); exit 1 with a message on stderr on failure or missing argument; newline-terminated. Source: https://raw.githubusercontent.com/microsoft/WSL/master/src/linux/init/wslinfo.cpp (master, not a release tag).
- Finding the console user's profile from a service: `WTSGetActiveConsoleSessionId()` (returns 0xFFFFFFFF if no console session is attached) -> `WTSQueryUserToken(sessionId, &token)` (needs LocalSystem plus SE_TCB_NAME; close the handle) -> `GetUserProfileDirectoryW(token, buf, &size)` (token needs TOKEN_QUERY; first call with NULL returns the needed size) -> `<profile>\.wslconfig`. Not confirmed: behaviour when the console session has no logged-on user (lock screen with nobody, RDP-only logins; WTSQueryUserToken fails, error code to handle). Sources: https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsqueryusertoken, https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-getuserprofiledirectoryw, https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-wtsgetactiveconsolesessionid
- `.wslconfig` location `%UserProfile%\.wslconfig`; it does not exist by default; if missing or malformed WSL starts with defaults. Keys live in section `[wsl2]`: `networkingMode` values `none`, `nat`, `bridged` (deprecated since WSL 2.4.5), `mirrored`, `consomme` (formerly `virtioproxy`); default `NAT`; an unknown value means NAT, and since WSL 2.3.25 a failed NAT start falls back to Consomme (so the effective mode can differ from the file: this is the "VirtioProxy fallback stays undetected" case). Values should be compared case-insensitively (docs write `NAT`/`nat`/`mirrored` interchangeably; key names in the docs example appear in mixed case such as `localhostforwarding`, so match keys case-insensitively too; I did not verify WSL's own case rules). `dnsTunneling` default `true`, Windows 11 22H2+ only; `networkingMode` and `dnsTunneling` are marked Windows 11 only (22H2+); `dnsProxy` (default true) applies to NAT only. Also `[experimental] dnsTunnelingIpAddress` default `10.255.255.254`. Source: https://learn.microsoft.com/en-us/windows/wsl/wsl-config (updated 2026-10-16) and https://learn.microsoft.com/en-us/windows/wsl/networking
- Changes need `wsl --shutdown` plus about 8 seconds to apply; the file can therefore disagree with the running VM.

## 5. Hetzner rules (frozen description `info.description`, line 7)

- Label key: optional prefix + `/` + name. Name: required, <= 63 chars, starts and ends with `[a-z0-9A-Z]`, `-`, `_`, `.` and alphanumerics between. Prefix (optional): DNS subdomain (DNS labels separated by dots), <= 253 chars, followed by `/`. Value: <= 63 chars, may be empty, otherwise starts and ends with `[a-z0-9A-Z]` with `-_.` and alphanumerics between. The prefix `hetzner.cloud/` is reserved and rejected. Examples in spec: `example.com/my=label`, `just-a-key=""`. Not stated in the spec: whether only one `/` is allowed (it is implied by "two segments"), max total count of labels per resource (not in the description; not confirmed).
- Label selector operators (complete list in spec): `k==v` and `k=v` (equal), `k!=v`, `k` (present), `!k` (absent), `k in (v1,v2,v3)`, `k notin (v1,v2,v3)`, and comma = AND (`k1==v,!k2`). There is no OR and no regex. Whitespace rules and quoting are not specified in the spec (examples use `env in (testing,staging)` with spaces around `in`). Query values must be URI-encoded; the live check in CONTEXT shows `!!!==` gives 422 `invalid_input`.
- Pagination: `page` first is 1; `per_page` default 25, maximum 50. Spec text: "For invalid values, page 1 is fetched" and "for invalid values, the default is used" (parameter schema: page minimum 1, per_page minimum 1, maximum 50). So the documented behaviour for `page=0`, `per_page=0` or `per_page=51` is a silent fallback, not an error. The spec does not say what a page beyond the last returns (expected: empty list, `next_page` null); NOT confirmed, and I did not call the real API. `meta.pagination` has `page, per_page, previous_page, next_page, last_page, total_entries`, all six required; the last four may be null (`previous_page` null on page 1; `next_page` and `last_page` null on the last page; `total_entries` null if unknown). The example response on the last/empty page shows `last_page: 1`, `next_page: null`. A `Link` header is deprecated (announced removal, changelog 2026-10-12) and can be omitted. The spec's own example writes `page_size`, a typo; the parameter is `per_page`.
- Sorting: `sort=<field>[:asc|:desc]`, repeatable, ascending by default, applied in order; contrary orders for the same field are ignored (documented). Per endpoint enum in the spec: servers `id, name, created` (each with `:asc`/`:desc`); placement_groups `id, name, created`; ssh_keys `id, name` only (no `created`); server_types: NO `sort` parameter and NO `label_selector` (only `name`, `page`, `per_page`).
- Other list filters in spec: servers `name`, `label_selector`, `status[]` (running, initializing, starting, stopping, off, deleting, migrating, rebuilding, unknown); placement_groups `name`, `label_selector`, `type[]` (spread); ssh_keys `name`, `fingerprint`, `label_selector`; server_types `name`.
- Placement group limits (docs, not spec): up to 10 servers per spread group, 50 groups per project, 1 group per server. Source: https://docs.hetzner.com/cloud/placement-groups/overview/
- Error for the eleventh server in a spread group: NOT found in the spec or docs. The only related documented code is `placement_error` (422, "An error during the placement occurred") in the `create_server` operation-specific errors (line 48587). Whether the real API answers `placement_error` or something else for a full group is unclear; do not claim it as confirmed.
- `add_to_placement_group` (`POST /servers/{id}/actions/add_to_placement_group`, body `{placement_group: <id>}`, spec line 54146): yes, the server must be powered off. Operation-specific errors: 422 `server_not_stopped` ("The action requires a stopped server") and 422 `already_in_placement_group` ("The server is already part of a placement group"). Success: 201 with an action. Remove is `remove_from_placement_group` (no off-requirement stated).
- Response codes: create ssh_key/placement_group 201, update 200, delete 204. `update_placement_group` doc note: concurrent change gives `conflict`.

## 6. Real `/server_types`

- Spec `list_server_types` (line 46275): query parameters `name`, `page`, `per_page` (default 25, min 1, max 50, same as every list endpoint); no sort, no label_selector. Response `server_types` plus `meta.pagination` (same ListMeta shape as in section 5: `page, per_page, previous_page, next_page, last_page, total_entries`). The general rule "maximum is 50 unless otherwise specified" is the only paging text; no endpoint-specific override found for server_types.
- hcloud-go and the CLI always send `per_page=50`; with 25 per page and a catalog of more than 25 types, hlab must page correctly or the CLI list would see only the first page only if `next_page` is wrongly null.
- The real number of server types and whether the live API returns all in one page is not confirmed (no live call by instruction).
