## Contradictions and corrections against CONTEXT (read first)

1. Gateway address (CONTEXT, Private IPs). CONTEXT says "gateway (first address of the range)". Hetzner's FAQ says the first IP of the *network's* `ip_range` is the gateway. The OpenAPI subnet schema says "for subnets of type server this is always the first IP of the subnet's IP range", but its own examples show subnet `10.0.1.0/24` with gateway `10.0.0.1`. Route gateways "cannot be the first IP of the networks ip_range". Use one gateway per network (first IP of the network range, which also fits one VRF per network). Reserved: that gateway, network and broadcast address of every subnet, `172.31.1.1`. Source: https://docs.hetzner.com/cloud/networks/faq and the spec (`create_network`). Whether the real API returns the network's first IP for every subnet is unclear (spec contradicts itself); an implementation that follows the FAQ and examples is the safer choice.
2. `change_ip_range` (CONTEXT: "grow only"). The spec adds: only the netmask may change (start address stays), and the network must have no attached members, otherwise `422 service_error`. `409 conflict` during a running change. Source: spec `change_network_ip_range`. Also: "To update the routes on the connected Servers, they need to be rebooted or routes updated manually" (no push to guests).
3. Primary IP / floating IP delete (CONTEXT does not state it). Since 2026-05-01 (already past) deleting an assigned primary or floating IP fails with `422 must_be_unassigned`; the server must also be powered off for primary IP delete. Also `change_protection` delete=true is only allowed when `auto_delete` is false (error code not documented). Source: spec `delete_primary_ip`, `delete_floating_ip`, `change_primary_ip_protection`.
4. Floating IP location rule (CONTEXT: "location/zone rules from Hetzner's docs"). The two Hetzner sources differ. OpenAPI: assignable to a server "in any Location". Docs FAQ: must be the same network zone. Neither names an error code for a zone mismatch; only `422 floating_ip_assigned` (already assigned) is documented. Treat the zone rule as the stricter docs rule and mark the error code as unclear (suggest `invalid_input`/`service_error` from the generic list, unconfirmed). Source: https://docs.hetzner.com/cloud/floating-ips/faq and spec `create_floating_ip`.
5. "like Hetzner's hc-utils" (Q1). Hetzner's mechanism is not metadata driven: a udev rule matches MACs `86:00:00:*` (`enx860000...`), tags the link, and starts `hc-net-ifup@<if>.service`, which runs `dhclient -1 -4`. A `hc-ifscan` script starts that unit for every `en*` link whose operstate is down. cloud-init >= 25.3 does the same natively on Ubuntu 22.04+ by triggering DHCP. So the outcome (adapter configured live, no reboot) matches the CONTEXT answer, but the hlab timer is a deliberate substitute (no DHCP server in hlab). Our `02:48:4c:2x` MACs never match the hc-utils rule, so a stock image with hc-utils will not start a competing dhclient. Sources: hc-utils repo (`81-hc-network-interfaces.rules`, `hc-ifscan`, `hc-net-ifup@.service` on branch `master`), https://docs.hetzner.com/networking/networks/server-configuration.
6. Proxy ARP (CONTEXT, Agent). `proxy_arp=1` alone does not answer ARP for a target whose route points out the *same* interface the request arrived on; that needs `proxy_arp_pvlan=1` ("allow proxy arp replies back to the same interface"). All members of a network share one VLAN subinterface, so peers are always same-interface targets. With the guest config from CONTEXT (/32 plus range route via gateway) guests only ARP for the gateway and never for peers, so proxy ARP matters only for HOST-01 (hand-made on-link routes). To make HOST-01 deterministic set both `proxy_arp` and `proxy_arp_pvlan`. Source: https://docs.kernel.org/networking/ip-sysctl.html. Behaviour inside a VRF not tested: unclear, needs an e2e probe.
7. No other contradiction. Confirmed as in CONTEXT: DELETE network detaches automatically, delete_subnet refused with attached resources, delete_route has no lock, Hetzner private MAC is `86:00:00:xx:xx:xx`, routes outside the network range are not delivered to guests.

## 1. Private adapter reaching a running guest (Hetzner)

- Mechanism: see contradiction 5. Interface names on Hetzner: `enp7s0`/`enp8s0`/`enp9s0` (newer types), `ens10..12` (older), `eth1..3` (CentOS 7). Up to 3 private interfaces. Source: server-configuration page above.
- DHCP: Hetzner's DHCP stopped sending the Router option (code 3) and sends only Classless Static Routes (option 121) so only the network prefix (e.g. `10.0.0.0/16`) is routed over the private interface; any default route via the gateway is the user's job. Seen through a search summary of Hetzner's "DHCP Bugfix" page; the page itself returned 404 on fetch, so the exact option contents (e.g. whether the gateway `/32` on-link route is included) are unclear.
- Manual config on Hetzner's page: address as `/32`, MTU 1450, route to the network range via the gateway (first IP of the network) marked on-link. Architecture page: `10.0.0.1/32` on-link, `10.0.0.0/16 via 10.0.0.1`. Use `GatewayOnLink=yes` / `ip route ... onlink`. Source: https://docs.hetzner.com/networking/networks/technical-concepts/architecture/.
- Routes: network routes with destinations inside the range apply automatically; routes with destinations outside the range "need to be added in each server's OS"; hc-utils rewrites config after reboot and removes manual routes. Confirms CONTEXT (routes not given to the guest). Alias IPs are never given by DHCP. Source: FAQ above.
- Private MTU 1450 (public 1500). Gateway enforces unicast RPF: source must be the server's own IP, alias IP, or a routed range where that server is the gateway (relevant to NET-03/NET-04 agent rules).
- Limits: 3 networks per server, 5 alias IPs per server (FAQ). Error codes for the limits are not documented; the generic `403 resource_limit_exceeded` is the likely one, unconfirmed.

## 2. Hetzner API rules (frozen spec)

- `attach_server_to_network`: auto IP from a subnet in the same `network_zone`; `alias_ips` must be configured by hand. Errors (422): `server_already_attached`, `ip_not_available`, `no_subnet_available` (no subnet or IP free, also the zone-mismatch case), `networks_overlap` (new network range overlaps one of the server's networks; so overlapping ranges are legal only across different servers). Attach/detach has no documented server-state condition (works running).
- `change_server_alias_ips`: replaces the full list. `detach_server_from_network`: "The interface for this network will vanish."
- `delete_network`: "Attached resources will be detached automatically." `update_network`, `add_route`, `delete_route`, `add_subnet`, `delete_subnet`: `409 conflict` while a change is running. `delete_subnet`: "Subnets containing attached resources can not be deleted" (error code not documented, unclear). Route destination: RFC1918 or `0.0.0.0/0`, must not overlap a subnet range, other route destinations or `172.31.1.1`; route gateway not the network's first IP, not behind a vSwitch, not `172.31.1.1`. Network minimum /24, subnet minimum /30, subnet default is first free /24. Delete protection: `423 protected`.
- `create_server`: `networks` (IDs), `public_net.enable_ipv4/enable_ipv6` (default true), `public_net.ipv4/ipv6` (Primary IP IDs; omitted + enabled creates a new one). Errors: `412 primary_ip_version_mismatch`, `422 primary_ip_assigned`, `422 primary_ip_datacenter_mismatch` (note: load balancers use `primary_ip_location_mismatch`). Error for "no public IPv4 and no network" is not in the spec: unclear.
- Primary IP: `assign` needs server `off` (`422 server_not_stopped`), already assigned elsewhere `primary_ip_already_assigned`, server already has that family `server_has_ipv4`/`server_has_ipv6`. `unassign`: server `off` (`server_not_stopped`), `server_is_load_balancer_target`; "a server requires at least one network interface (public or private) to be powered on". `create`: with `assignee_id/assignee_type` assigns (same errors as assign) or needs `location`; assignable only within the same location later. `auto_delete` (default false): deleted once the assigned resource is deleted. `delete_server`: attached Primary IPs/Floating IPs are detached; auto_delete ones are removed.
- Floating IP: `create` takes `server` or `home_location` (mutually exclusive; `type` required); `assign` errors `422 floating_ip_assigned`; `unassign`: IP becomes unreachable, can be reassigned; `delete`: see contradiction 3. Floating IPs are configured by the user inside the guest (FIP-02 ok).
- Generic codes available in the spec: 403 `resource_limit_exceeded`, 409 `conflict`/`uniqueness_error`, 422 `invalid_input`/`service_error`/`unsupported_error`, 423 `locked`/`protected`.
- "Lowest free host address" allocation is not documented anywhere I found: unclear (keep as decision, record in DECISIONS.md).

## 3. Hyper-V

- `Set-VMNetworkAdapterVlan`: Access, Trunk, PVLAN (Isolated/Community/Promiscuous) and Untagged are mutually exclusive per adapter, i.e. a mode is per port, so mixed port modes on one switch are by design. Trunk syntax: `-Trunk -AllowedVlanIdList "2-4092" -NativeVlanId 0` (docs say Trunk is used with AllowedVlanIdList and NativeVlanId; Example 2 uses both). Access: `-Access -VlanId N`. Source: https://learn.microsoft.com/en-us/powershell/module/hyper-v/set-vmnetworkadaptervlan. No document states explicitly that trunk and PVLAN ports coexist on the same internal switch: unclear, needs an e2e probe (the existing PVLAN appliance port stays untouched; the trunk is a second adapter).
- Hot add/remove: Microsoft states Windows Server 2016+ can hot add/remove network adapters on running Generation 2 VMs, any supported guest. Source: https://learn.microsoft.com/en-us/windows-server/get-started/whats-new-in-windows-server-2016 and the feature compatibility page. `Add-VMNetworkAdapter -VMName -Name -SwitchName -StaticMacAddress -DeviceNaming On` (also `Remove-VMNetworkAdapter`). Whether this works without elevation as a Hyper-V Administrators member: unclear (cmdlet pages state no elevation requirement; not testable here).
- MAC ACL: `Add-VMNetworkAdapterAcl -VMName/-VMNetworkAdapter -RemoteMacAddress aa-bb-cc-dd-ee-ff -Direction Both -Action Deny`. "Remote" MAC = source on inbound, destination on outbound, so `Both` drops traffic to and from that peer (also broadcasts it sends). Entries with no match fall through to allow; the appliance trunk MAC is never listed, so routed traffic through the appliance stays allowed. Removal: `Remove-VMNetworkAdapterAcl` (parameters must match the entry; not read in detail), `Get-VMNetworkAdapterAcl` to list. Whether ACL changes on a running adapter and duplicate Add are accepted without elevation is unclear. Source: https://learn.microsoft.com/en-us/powershell/module/hyper-v/add-vmnetworkadapteracl. Pitfall: the doc says the "longest match rule decides" for IP ACLs; MAC-only entries are exact matches so no precedence issue.
- Stable MAC per adapter must be set statically (`-StaticMacAddress`), otherwise the deny entries do not follow a re-added adapter.

## 4. Linux appliance

- VRF: `ip link add vrf-X type vrf table N`; enslave the VLAN subinterface (`master vrf-X`); one l3mdev rule handles lookups; connected/local routes move into the VRF table on enslave, other routes on that interface are dropped and must be re-added afterwards. Overlapping ranges across VRFs work (separate FIB tables, ARP/neighbour tables are per device). Source: https://docs.kernel.org/networking/vrf.html.
- netlink v1.3.1 (published 2025-05-09, latest release): `netlink.Vrf{LinkAttrs: netlink.LinkAttrs{Name: ...}, Table: uint32}`; `netlink.Vlan{LinkAttrs{Name, ParentIndex}, VlanId int, ...}`; `LinkSetMasterByIndex(link, vrfIndex)` (for VRFs the field is still named MasterIndex); route fields `Table`, `LinkIndex`, `Gw`, `Scope`, `Flags`; on-link flag `netlink.FLAG_ONLINK` (type `NextHopFlag`, set via `route.SetFlag`/`Flags`; exact setter not read: confirm when coding). Source: raw `link.go`, `route_linux.go` at v1.3.1.
- Sysctls per subinterface: `net.ipv4.conf.<if>.proxy_arp=1`, `send_redirects=0`, `accept_redirects=0`, plus `forwarding=1`; keep `rp_filter` consistent (0 or 2 on the subinterfaces, since the same-interface forward path would fail strict mode). Source: ip-sysctl page above.
- Metadata server per VRF: bind each listener with `SO_BINDTODEVICE` to the VRF device (kernel doc: "bind a socket to the VRF device"); in Go use `net.ListenConfig{Control: ...}` with `unix.SetsockoptString(fd, SOL_SOCKET, SO_BINDTODEVICE, "vrf-X")`. Two listeners on the same address:port in different VRFs are possible because the bound device differs. Unprivileged SO_BINDTODEVICE needs Linux >= 5.7 (from memory; the agent runs as root anyway). Alternative: one listener in the default VRF with `net.ipv4.tcp_l3mdev_accept=1` (child sockets inherit the L3 master index), but the doc says which listener wins when both exist is unspecified, and overlapping gateway addresses make it ambiguous: prefer a listener per VRF. Identify the caller by (VRF, remote IP) from the accepting listener.
- nftables (google/nftables v0.3.0, published 2025-02-03; the repo has only tags v0.1.0..v0.3.0, so no newer tag exists, v0.3.0 is current, last release about 21 months ago): `expr.Meta` keys available: `MetaKeyIIFNAME`, `MetaKeyIIF`, `MetaKeyOIFNAME`, `MetaKeyOIF`, `MetaKeyIIFTYPE`... but NOT `MetaKeyIIFKIND`/`MetaKeyOIFKIND`, so a "vrf kind" match is not available through the typed API; match the VLAN subinterface by name/index instead. Concatenated sets exist: `nftables.ConcatSetType(types ...SetDatatype)`, `TypeIFName`, `TypeEtherAddr`, `TypeIPAddr`, `Set.Interval`, `SetElement.IntervalEnd`; so a set of `iifname . ether saddr . ipv4 saddr` (the MAC/IP pair per VLAN backstop) is expressible. Field name is `Set.Concatenation`.
- Netfilter in VRF (kernel doc): PREROUTING sees the real ingress device; INPUT sees the VRF device; forwarded packets do not go through the VRF device. A 2021 kernel thread shows `iif` in raw prerouting and conntrack zone assignment changed between kernel versions when the VRF hook re-runs (regression test `tools/testing/selftests/netfilter/conntrack_vrf.sh`). Rules on ingress should key on the slave subinterface name at prerouting/forward, not the VRF device. Which kernel the appliance image uses is not checked here.
- Pitfall (source: kernel mailing list thread and VyOS notes, not a normative doc): overlapping addresses in different VRFs collide in conntrack (same 5-tuple). If the nftables rules use `ct state`, put each VRF in its own conntrack zone (`ct zone set` in a raw-priority prerouting chain keyed on iifname), or stay stateless (pure per-packet MAC/IP/VLAN matching), which the backstop described in CONTEXT can be. Unclear: whether routed (forwarded) traffic between overlapping networks already goes through conntrack on the appliance without any `ct` rule; conntrack is loaded as soon as an nft `ct` expression or NAT exists.

## 5. cloud-init (NoCloud)

Versions found 2026-11-19: Ubuntu 22.04 jammy 26.1, 24.04 noble 26.2, 26.04 resolute 26.2 (Launchpad); Debian 12 bookworm 22.4.2, Debian 13 trixie 25.1.4, testing 26.2 (tracker.debian.org). Release numbers are those in the archives, the cloud images may lag.

- Config: `updates: network: when: [boot]` (events `boot-new-instance`, `boot`, `boot-legacy`, `hotplug`). Docs say "may be specified via user-data". Source (main branch, `stages.py`): `update_event_enabled` reads `cfg["updates"]` from `self.cfg`, which merges `cloud-config.txt`, `vendor2-cloud-config.txt`, `vendor-cloud-config.txt` from the instance dir plus the base system config; user config overrides datasource defaults. So a vendor-data `updates` block works from the second boot (the files are written on the first boot), not on the first boot itself, and the docs do not mention vendor-data: source-derived, untested. A drop-in under `/etc/cloud/cloud.cfg.d/` in the image is the documented-by-code, safest alternative for images hlab controls.
- NoCloud does not override `supported_update_events`/`default_update_events` (base class: supported = boot-new-instance, boot, boot-legacy, hotplug; default = boot-new-instance only). With `boot` enabled, `apply_network_config` calls `update_metadata_if_supported([BOOT])`, which clears cached metadata and re-runs `get_data()`, so the network-config in the (rebuilt) CIDATA ISO is read again and rendered on a normal reboot. `check_instance_id` for NoCloud only looks at seed directories and the kernel command line, not the ISO, so cloud-init re-discovers the datasource every boot anyway (source-derived).
- SSH host keys: regenerated only for a new instance (instance-id change); the docs say the instance-id is what decides "first boot". Keep `instance-id` in `meta-data` stable when only `network-config` changes (or at least stable per VM), then per-instance modules (including `ssh` key generation) do not rerun. Not tested; the docs pages did not explicitly address host keys.
- Changes to `user-data`/`vendor-data` do not re-apply without a new instance-id (NoCloud docs); only network config is re-rendered via the `boot` event.
- cloud-init `hotplug`: needs datasource support and `updates` config; it re-reads the datasource, so a live-changing seed ISO would be needed. Not suited here; the hlab-guest timer from CONTEXT stays the right design.
- Guest timer to configure a hot-added NIC live (design suggestion, not verified on images): match by MAC (names differ on Hyper-V: `ethN` or `enx<mac>`; `NamePolicy`/`ID_NET_NAME` are unreliable), write a file to `/run/systemd/network/05-hlab-<mac>.network` (volatile, so it never conflicts with the seed-rendered config after the next boot; sorts before netplan's `10-netplan-*`): `[Match] MACAddress=..` `[Network] Address=<ip>/32` `[Route] Destination=<range> Gateway=<gw> GatewayOnLink=yes` `[Link] MTUBytes=1450` (optional), then `networkctl reload` and `networkctl reconfigure <if>` (systemd >= 244; present on 22.04 and later, Debian 12 has 252). On removal delete the file and reload. Ubuntu cloud images use netplan/networkd; Debian 12 cloud images use the ENI renderer through cloud-init 22.4.2 (ifupdown) and may not run networkd, Debian 13 renderer unconfirmed. Therefore keep a fallback with plain `ip addr replace <ip>/32 dev <if>` and `ip route replace <range> via <gw> dev <if> onlink` for hosts where networkd is not active. Distribution defaults per image: unclear until checked in e2e.
